# 对 `const` 对象使用 `std::move`

## 1. 问题描述

很多 C++ 代码把 `std::move` 当作“强制移动”的开关。
这是常见误解。

`std::move` 本质是类型转换工具，
它不会直接移动资源。

当对象是 `const` 时，`std::move` 往往无法触发真正的移动语义，
最终仍走拷贝路径。

这会导致两类问题：

1. 性能错觉（代码看起来在优化，实际上没有）；
2. API 所有权语义混乱（签名表达借用，实现却试图转移）。

---

## 2. 讨论边界

### 2.1 本文覆盖

1. `std::move(const T&)` 为何常常拷贝；
2. 重载决议如何导致该结果；
3. 所有权转移 API 的正确设计方式；
4. 代码评审与迁移策略。

### 2.2 本文不覆盖

并非断言“任何类型都不能从 const 移动”。
少数类型可定义 `const T&&` 相关重载，但工程上非常少见且不推荐依赖。

---

## 3. 最小示例

```cpp
#include <string>
#include <utility>

void f(const std::string& s) {
    std::string x = std::move(s); // 实际通常是拷贝
}
```

`std::move(s)` 的类型是 `const std::string&&`。
而 `std::string` 的移动构造通常是 `std::string(std::string&&)`。

`const std::string&&` 无法绑定到 `std::string&&`，
所以最终匹配的是拷贝构造。

---

## 4. 语言机制拆解

### 4.1 `std::move` 的本质

概念上它是：

```cpp
template <class T>
constexpr std::remove_reference_t<T>&& move(T&& t) noexcept;
```

它只改变值类别，不改变 `const` 属性。

### 4.2 const 会被保留

若输入是 `const T&`，输出是 `const T&&`。
并不会变成 `T&&`。

### 4.3 为什么移动构造通常不能接 const

移动语义常需要修改源对象（清空指针、重置状态等）。
`const` 禁止这种修改，因此大多数移动构造不接受 `const T&&`。

---

## 5. 重载决议结果

典型构造集合：

```cpp
T(const T&); // 拷贝
T(T&&);      // 移动
```

对 `const T&&` 实参：

1. `T(T&&)` 不可行；
2. `T(const T&)` 可行；
3. 选择拷贝路径。

因此，“写了 `std::move`”不等于“发生了移动”。

---

## 6. 为什么这个坑很常见

### 6.1 视觉误导

代码里出现 `std::move`，评审者容易下意识认为已优化。

### 6.2 签名与意图冲突

函数签名是 `const T&`（借用），实现却尝试移动（转移）。
语义本身互相矛盾。

### 6.3 编译器通常不报错

该问题常是“合法但低效/误导”的代码路径，
难以靠编译错误自动暴露。

---

## 7. 观测示例

```cpp
#include <iostream>
#include <utility>

struct X {
    X() = default;
    X(const X&) { std::cout << "copy\n"; }
    X(X&&) noexcept { std::cout << "move\n"; }
};

void g(const X& x) {
    X y = std::move(x); // 常输出 copy
}
```

该示例可直观说明“const + move 仍走拷贝”。

---

## 8. 伪优化反模式

```cpp
void set_name(const std::string& s) {
    name_ = std::move(s); // 通常仍是拷贝赋值
}
```

这类代码会误导维护者，对性能无实质帮助。

---

## 9. 正确模式：按值接收 + 内部移动

```cpp
void set_name(std::string s) {
    name_ = std::move(s);
}
```

语义清晰：

1. 调用方若传右值，可高效转移；
2. 调用方若传左值，付出一次拷贝成本。

该模式通常是 sink API 的优雅默认方案。

---

## 10. 重载方案

也可使用显式重载：

```cpp
void set_name(const std::string& s) { name_ = s; }
void set_name(std::string&& s) noexcept { name_ = std::move(s); }
```

适用于需精细区分调用路径的场景。

---

## 11. 完美转发并不会绕过 const

```cpp
template <class T>
void sink(T&& x) {
    consume(std::forward<T>(x));
}
```

若调用方传 `const T&`，转发后仍保留 const。
因此下游仍无法进行“可修改源对象”的移动。

---

## 12. 返回 `const T` 的问题

返回值声明成 `const T` 通常弊大于利：

1. 可能阻碍后续移动路径；
2. 增加语义复杂度；
3. 对安全性贡献有限。

一般应返回 `T`。

---

## 13. moved-from 状态与 const

移动后对象需保持“有效但状态未指定”。
该过程通常要求修改源对象状态。

`const` 禁止状态修改，
因此“从 const 移动”在语义上天然受限。

---

## 14. 是否能支持 `const T&&`

理论上可以定义相关重载，
但通常无法真正偷取资源，且会增加接口认知成本。

工程上不建议依赖这种非常规设计。

---

## 15. 容器元素 const 场景

某些容器语境下元素部分是 const（如关联容器 key）。
对这些 const 子对象调用 `std::move` 也通常无法走真实移动路径。

需先理解元素 cv 约束，再谈优化。

---

## 16. 与并发无直接等价

`const` 不等于线程安全；
“不能从 const 移动”也不等于并发安全。

不要把 const 语义与同步语义混淆。

---

## 17. 诊断建议

可通过以下方式发现伪移动：

1. 审查 `const T&` 函数体内 `std::move`；
2. 启用相关编译器告警/静态分析规则；
3. 对关键路径做 copy/move 计数基准。

---

## 18. 高频反模式清单

1. 对 `const` 局部变量 `std::move`；
2. 在借用签名中试图移动参数；
3. 返回 `const T` 并期待后续高效移动；
4. 将 `const` 当作默认装饰而非语义约束；
5. 误以为完美转发自动开启移动路径。

---

## 19. 设计准则

1. 想转移所有权，就不要使用 `const T&` 作为输入合同；
2. sink API 默认考虑“按值接收 + 内部移动”；
3. 仅在非 const 且语义允许时使用 `std::move`；
4. const 只用于表达逻辑不可变性；
5. 在文档中明确借用与拥有边界。

---

## 20. 旧代码迁移路径

1. 检索 `std::move` 出现在 `const T&` 函数中的位置；
2. 区分借用型 API 与 sink 型 API；
3. sink API 改为按值或右值重载；
4. 借用 API 保持显式拷贝语义；
5. 对关键模块重测性能。

---

## 21. 代码评审清单

- [ ] `std::move` 是否作用于 const 对象？
- [ ] 函数签名是否与所有权意图一致？
- [ ] sink 场景是否采用按值/右值设计？
- [ ] 借用场景是否避免伪移动误导？
- [ ] 性能结论是否有实测依据？

若任一项不明确，应先修正接口语义。

---

## 22. 实务结论汇总

1. `std::move` 是 cast，不是移动动作；
2. `std::move(const T&)` 常常仍是拷贝路径；
3. 所有权转移应在签名层表达；
4. 按值接收是很多 sink API 的稳健默认；
5. 优化必须基于语义正确与性能测量。

---

## 23. 总结

“对 const 使用 move”是 C++ 中非常典型的语义错觉。
问题不在语法，而在合同：

1. `const` 表示不可修改；
2. 真正移动通常需要修改源状态；
3. 两者冲突时，编译器自然回落到拷贝。

稳定的工程实践应先设计正确的所有权接口，再使用 `std::move`。
这样得到的性能优化才是“真实且可维护”的，而不是表面化装饰。
