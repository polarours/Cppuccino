# 数据竞态

## 1. 引言

**数据竞态（data race）** 发生在两个或更多线程并发访问同一块内存，其中至少一个是写操作，且没有同步操作来给这些访问排序。在 C++ 中，数据竞态属于**未定义行为**——程序可能产生任何结果、崩溃，或者大多数时候看似正常、只在偶尔情况下失败。

这是最常见也最危险的一类并发 bug，因为它在普通测试中可能完全不可见，只在特定的调度、特定的硬件，或一次看似无害的编译器优化之后才暴露出来。

## 2. 问题

```cpp
#include <thread>
#include <vector>

int counter = 0;

void worker() {
    for (int i = 0; i < 100'000; ++i) {
        ++counter;  // 对共享变量的读-修改-写，没有任何同步
    }
}

int main() {
    std::vector<std::thread> threads;
    for (int t = 0; t < 10; ++t)
        threads.emplace_back(worker);
    for (auto& th : threads)
        th.join();

    // 期望：counter == 1'000'000
    // 现实：往往是一个更小的数，并且在标准层面是未定义行为
}
```

### 为什么出错

`++counter` 不是原子的。它被展开为三步操作：从内存读取 `counter`、加 1、写回内存。当两个线程并发执行时：

- 线程 A 读到 `counter == 5`
- 线程 B 读到 `counter == 5`
- 线程 A 写入 `6`
- 线程 B 写入 `6`

其中一个线程的递增被丢掉了。更糟的是，因为数据竞态是未定义行为，编译器可以自由地按"没有其他线程会碰 `counter`"来优化这个循环（例如把它提升进寄存器），硬件也可能重排或缓存这个值。结果不只是"偶尔算错"——它在标准层面是未指定的。

## 3. 修复

### 3.1 对单个变量使用 `std::atomic`

```cpp
#include <atomic>
#include <thread>
#include <vector>

std::atomic<int> counter{0};

void worker() {
    for (int i = 0; i < 100'000; ++i) {
        ++counter;  // 原子的读-修改-写，行为良好定义
    }
}
```

### 3.2 需要保护复合不变式时使用互斥锁

```cpp
#include <mutex>

int counter = 0;
std::mutex mtx;

void worker() {
    for (int i = 0; i < 100'000; ++i) {
        std::lock_guard<std::mutex> lock(mtx);
        ++counter;
    }
}
```

当被保护的部分涉及不止一个原子变量时（例如在两个账户间转账，或者更新计数器的同时更新时间戳），应使用互斥锁。

## 4. 如何检测数据竞态

在 **ThreadSanitizer**（GCC 和 Clang 均支持）下运行测试：

```bash
g++ -fsanitize=thread -g -O1 main.cpp -o main
./main
```

ThreadSanitizer 会报告确切的两条竞态访问及其调用栈，这比手动复现 bug 可靠得多。

## 5. 最佳实践

1. **最小化共享的可变状态**——尽可能按值传递数据，或使用线程局部存储。
2. **单个计数器、标志、指针优先用 `std::atomic`**。
3. **复合不变式用 `std::mutex`（或 `std::shared_mutex`）**。
4. **在 CI 中用 ThreadSanitizer 测试**，再宣布并发代码安全。
5. **记录所有权**——哪些数据由哪个线程拥有，哪些被共享。

## 6. 总结

- 数据竞态 = 未同步的并发访问，且至少一个是写操作。
- 它是**未定义行为**，而不只是"偶尔算错"。
- 用 `std::atomic`（单个位置）或 `std::mutex`（复合状态）修复。
- ThreadSanitizer 是发现测试无法暴露的竞态最快的方式。
