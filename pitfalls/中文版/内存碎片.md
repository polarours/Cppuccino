# 内存碎片

## 引言

所谓**碎片（fragmentation）**，是指空闲内存总量上存在，却没有足够大的**连续**块来满足一次分配。在一个长时间运行的程序里，如果它反复分配、释放**大小不一**的块，堆就会被切成许多被存活对象隔开的「小空洞」。最终即便空闲字节的总和足够，`new` 也会失败（抛出 `std::bad_alloc` 或返回 `nullptr`）——因为它们散落各处，凑不出一块连续内存。

碎片是一个**吞吐量与可靠性**问题：它浪费内存，并且可能让一个「平稳运行了几小时」的服务崩溃。

## 问题

```cpp
#include <vector>

// 分配许多大小不一的小缓冲区，然后释放其中 *每隔一个* 的那一个。
void churn() {
    std::vector<int*> blocks;
    for (int i = 0; i < 1000; ++i) {
        blocks.push_back(new int[1 + (i % 8)]);   // 大小 1..8 个 int，交错排列
    }
    for (size_t i = 0; i < blocks.size(); i += 2) {
        delete[] blocks[i];                       // 释放奇数下标，保留偶数下标
        blocks[i] = nullptr;
    }
    // 此刻堆里有 500 个大小不等的空闲洞，与 500 个存活块交错。
    // 之后若请求一块 *大* 的连续内存，即便空闲 RAM 充足也可能失败。
}
```

**为什么出错：**
- 默认的 `::operator new` 从通用堆分配。混合的生命周期与大小会把空闲空间切得七零八落。
- 释放每隔一个块，会让存活块夹在已释放的空洞之间，于是没有任何一个空洞大到能满足一次大分配——典型的外部碎片。
- 对微小对象反复 `new`/`delete` 也会给分配器加压，随时间加剧碎片。

这种模式在解析器、请求处理器、以及每个 tick 都构造并销毁许多混合大小对象的游戏循环里非常常见。

## 修复

从一块按你**真实**工作集大小划出的区域分配，使用**池 / 内存池（arena）分配器**，使每个块都来自同一块连续缓冲区，并整体释放：

```cpp
#include <memory>
#include <memory_resource>
#include <vector>

// C++17 多态分配器：单调缓冲区以零逐次分配开销发出内存，且 **没有** 碎片，
// 因为没有单个对象被单独释放——整个缓冲区一次性回收。
void churn() {
    std::vector<char> arena(64 * 1024);                    // 一块连续区域
    std::pmr::monotonic_buffer_resource pool(arena.data(), arena.size());
    std::pmr::vector<int> blocks(&pool);                   // 由该池支持

    for (int i = 0; i < 1000; ++i) {
        blocks.resize(blocks.size() + 1 + (i % 8));        // 在 arena 内增长
    }
    // 没有逐元素释放 -> 没有碎片。当 `arena` 离开作用域时，一切以 O(1) 回收。
}
```

对**固定类型**的对象池，一个 `std::vector<T>`（连续存储）或一个复用 `T` 实例的空闲链表，能在分配之间彻底避开通用堆。

## 最佳实践

- **按生命周期把分配分组。** 把一次「tick」/请求所需的一切从一个 arena 分配，然后一次性释放该 arena。批量释放消除碎片。
- **优先用连续容器。** `std::vector<T>`（而非每个元素都 `new` 的 `std::vector<T*>`）把数据保存在一个块里，对缓存也更友好。
- **在热路径上用 `std::pmr`。** `std::pmr::monotonic_buffer_resource` / `std::pmr::unsynchronized_pool_resource`（C++17）几乎零成本地给你池/arena 行为。
- **复用对象。** 空闲链表或对象池回收已释放的实例，而不是把它们退回通用堆——对固定大小的结构尤其好。
- **测量，别猜。** 在真实负载下跟踪峰值 RSS 与分配器统计；碎片只在规模上显现，所以要用生产级强度的 churn 来测试。

## 总结

碎片是在通用堆上混合许多大小不同、时机不同的分配所交的「 silent 税」。你无法「修复」堆本身；你改变的是**如何分配**：给工作的每个阶段一块自己的 arena，再整体批量回收；把同构数据连续地放在 `std::vector` 里；在热路径上用 `std::pmr` 池。做到这些，「明明有空闲内存却分配失败」的崩溃就消失了。
