# 双重释放

## 引言

**双重释放（double free）** 指对同一个指针（或其副本）调用了超过一次的 `delete`。结果是**未定义行为**：内存分配器的内部簿记被破坏，可能立即崩溃、破坏毫不相干的数据，甚至留下可供攻击者借以控制进程的漏洞。

双重释放尤其阴险，因为程序往往**看起来还能正常跑一阵**——破坏可能很久之后、远离出错那一行时才爆发。

## 问题

```cpp
void cleanup() {
    int* p = new int(42);
    int* q = p;          // (1) q 是 p 的别名 —— 但它并不拥有独立的对象

    delete p;            // (2) 这个 int 被释放
    delete q;            // (3) 双重释放：q 指向同一块已被释放的 int -> 未定义行为
}
```

更现实的一种变体：把裸指针传给一个「善意的」会 delete 它的函数，而调用方又自己 delete：

```cpp
void consume(int* data) {
    // ... 使用 data ...
    delete data;         // (a) 接收了所有权，调用方不能再 delete
}

void caller() {
    int* x = new int(7);
    consume(x);
    delete x;            // (b) 双重释放：x 已在 consume() 内部被释放
}
```

**为什么出错：**
- 第一个例子里的 `q` 只是同一块分配的另一个名字。`delete q` 释放的是已经回到分配器空闲链表的内存。
- 分配器之后可能把同一块内存交给后面的 `new`，于是第二次「释放」和后面的「分配」互相破坏了对方的元数据。语言层面没有安全网——编译器不会警告，程序也可能先通过你的测试，再到生产环境才出错。

## 修复

唯一稳健的修复是让所有权明确，使指针**恰好被自动释放一次**：

```cpp
#include <memory>

void consume(std::unique_ptr<int> data) {
    *data += 1;   // unique_ptr 拥有这个 int；我们可以自由地读取/修改它
    // ... 并且它在函数返回时被自动释放 ...
}   // 此处 data 被析构；无论发生什么，恰好释放一次

void caller() {
    auto x = std::make_unique<int>(7);
    consume(std::move(x));   // 所有权转移；x 现在为空
    // 不可能再 delete x —— 它什么都不拥有
}
```

如果暂时无法迁移到智能指针，请严守纪律：**裸指针要么是被借用者（借用者绝不 delete），要么是恰好一个站点拥有（恰好 delete 一次）。** 明确这一点，绝不让两个站点都以为自己拥有同一个裸指针。

## 最佳实践

- **用 `std::unique_ptr` 拥有，用 `std::unique_ptr` 或裸观察指针传递。** 当函数要获取所有权时，以 `std::unique_ptr` **按值**接收——类型本身就能阻止双重释放。
- **绝不 delete 一个你没分配过的裸指针，也绝不 delete 同一个裸指针两次。** 这听起来显然，但别名和「善意的」delete 恰恰会破坏它。
- **`std::shared_ptr` 不是双重释放的许可证。** 两个 `shared_ptr` 必须共享**同一个**控制块（通过 `make_shared` 一同创建，或其中一个由另一个拷贝构造）。用同一个裸指针重新构造一个 `shared_ptr` 会得到两个独立的拥有者 → 双重释放。永远拷贝 `shared_ptr`，绝不要重新包装它的 `get()` 裸指针。
- **对危险的重载使用 `= delete`。** 如果一个类管理着资源，删除它的拷贝操作或正确实现它们；被静默拷贝的裸指针就是一颗等待引爆的双重释放炸弹。
- **用 sanitizer 抓它。** AddressSanitizer（`-fsanitize=address`）能在运行时检测到双重释放，并直接指向两个 `delete` 现场。

## 总结

双重释放发生在两段代码各自以为自己拥有同一块内存时。解决办法是让所有权**无歧义且唯一**：每个资源一个 `std::unique_ptr`，在边界处被移动（而非拷贝、而非别名）传递。当所有权被编码进类型系统，释放两次就从「需要记住的事」变成了「不可能发生的事」。
