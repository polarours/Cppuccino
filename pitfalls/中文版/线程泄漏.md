# 线程泄漏

## 1. 引言

**线程泄漏（thread leak）** 指线程被创建后从未被正确回收。它有两种危害形式：一是 `std::thread` 对象在仍处于可连接（joinable）状态时就被销毁，这会调用 `std::terminate` 直接中止程序；二是线程被 `detach` 后放任自流地运行，悄悄消耗资源直到进程退出。

线程泄漏会浪费内存、栈空间和文件描述符，最终可能耗尽系统的线程上限。

## 2. 问题

### 2.1 销毁一个可连接的线程

```cpp
#include <thread>

void task() { /* ... */ }

void spawn() {
    std::thread t(task);
    // 糟糕：t 在离开作用域前既没有 join() 也没有 detach()
}  // 这里会调用 std::terminate() —— 程序直接崩溃
```

`std::thread` 的析构函数在对象仍可连接时会调用 `std::terminate()`。这是硬崩溃，而不是悄悄的泄漏。

### 2.2 detach 后遗忘

```cpp
void spawn_detached() {
    std::thread t([] {
        do_long_work();  // 在"后台"运行
    });
    t.detach();  // 此后无法再 join 或监控它
}
```

`detach()` 之后，线程独立地一直运行。如果它捕获了已经离开作用域的局部变量的指针或引用，就会变成 use-after-free。即便内存安全，被 detach 的线程也会越积越多，并且难以干净地关闭。

## 3. 修复

### 3.1 始终通过 RAII 包装器 join

把线程包起来，让它在作用域结束时自动 join：

```cpp
#include <thread>

class joining_thread {
    std::thread t_;
public:
    explicit joining_thread(std::thread t) : t_(std::move(t)) {}
    ~joining_thread() { if (t_.joinable()) t_.join(); }
    // operator= 等转发接口从略
};

void spawn() {
    joining_thread t{std::thread(task)};  // 在作用域结束时自动 join
}
```

### 3.2 使用 `std::jthread`（C++20）

`std::jthread` 会在析构时自动 join——无需手写 RAII，并且还支持通过停止令牌（stop token）做协作式取消：

```cpp
#include <thread>

void spawn() {
    std::jthread t(task);  // 在作用域结束时自动 join
}
```

### 3.3 显式管理生命周期

如果你确实需要长期运行的线程，把它们放进一个容器，给它们一个关闭标志，并在拆解（teardown）时统一 join。

## 4. 最佳实践

1. **绝不要让 `std::thread` 在可连接状态下离开作用域。**
2. **优先用 `std::jthread`**（C++20）或带 join 的 RAII 包装器。
3. **避免 `detach()`**，除非你对捕获数据的生命周期有完整交代。
4. **把线程登记到一个注册表**，以便在关闭时统一 join。
5. **用停止令牌 / 标志**做协作式取消。

## 5. 总结

- 可连接的 `std::thread` 被销毁 = `std::terminate()`（崩溃）。
- `detach()` 会丢失控制权，并可能在捕获的局部变量上引发 use-after-free。
- 用 `std::jthread` 或带 join 的 RAII 包装器修复。
- 始终保留一条能干净 join 所有线程的关闭路径。
