# 有符号整数溢出假设

## 0. 范围与前置结论

本文聚焦一个极常见的 C++ 误区：

- 代码把有符号整数当作“必然补码回绕”处理；
- 编译器按“程序不会触发 UB”做优化；
- 最终行为与开发者直觉发生偏离。

本文边界：

1. 只讨论标准 C++ 语义下的有符号溢出；
2. 不默认任何编译器扩展的“强制回绕模式”；
3. 先讲规则，再讲工程实践。

核心结论：

- 标准 C++ 中，有符号溢出是未定义行为（UB）；
- 一旦 UB 可达，优化器可进行看似反直觉但合法的变换；
- 安全做法是证明“不溢出”或使用显式“可检查/模运算”语义。

---

## 1. 先立规则：语言到底怎么定义

对有符号整数类型（`int`、`long`、`long long` 等），当算术结果不可表示时，行为未定义。

典型触发点：

- `x + y` 超出可表示范围；
- `x - y` 超出可表示范围；
- `x * y` 超出可表示范围；
- 对最小值取负（如 `-INT_MIN`）。

必须严格区分：

- **无符号溢出**：按 $2^N$ 取模，行为有定义；
- **有符号溢出**：UB，无回绕保证。

不要把无符号规则迁移到有符号代码。

---

## 2. 为什么优化会“激进到离谱”

编译器做优化时，默认前提是：

$$
	ext{已定义程序执行路径不应触发 UB}
$$

因此它会推导：

1. 若某分支意味着有符号溢出，则该分支在“良定义程序”中不可达；
2. 不可达分支可删；
3. 条件可折叠，控制流可重排，进一步触发 DCE/内联等优化。

这类结果看上去像“编译器改坏了逻辑”，本质上是 UB 前提下的合法变换。

---

## 3. 典型误导示例

```cpp
int f(int x) {
    return x + 1 > x; // 可能被优化为恒真
}
```

在“无 UB”假设下，优化器可能这样推理：

- 若 `x == INT_MAX`，`x + 1` 会溢出；
- 触发 UB 的输入在良定义路径中被排除；
- 剩余输入上 `x + 1 > x` 恒成立；
- 因此可直接返回真。

这并非优化器“猜错”，而是源码先违反了可定义语义边界。

---

## 4. 真实工程中的高频形态

### 4.1 先算后查

```cpp
int add_bad(int a, int b) {
    int c = a + b; // 可能已 UB
    if (c < a) {
        // 试图补救，但时序已晚
    }
    return c;
}
```

问题：检查发生在潜在 UB 之后。

### 4.2 上界循环计数

```cpp
for (int i = start; i <= end; ++i) {
    // end == INT_MAX 时边界递增可能溢出
}
```

### 4.3 乘法参与长度/容量计算

```cpp
int n = rows * cols; // 可能溢出
std::vector<int> v(static_cast<std::size_t>(n));
```

会把算术错误传导到内存分配与边界检查路径。

### 4.4 最小值取负

```cpp
int abs_bad(int x) {
    return x < 0 ? -x : x; // x == INT_MIN 时 UB
}
```

### 4.5 哨兵值加偏移

```cpp
int timeout = base + delta; // base 靠近 INT_MAX 时高风险
```

代码暗含“会回绕”的错误前提。

---

## 5. “全换 unsigned”不是通用解

常见修复冲动是把所有整型换成无符号。

此做法常引入新问题：

1. 模运算语义未必符合业务含义；
2. 有符号/无符号混比触发隐式转换陷阱；
3. 负值哨兵与错误码语义被破坏。

是否用无符号，取决于领域语义，而不是“躲 UB”本能。

---

## 6. 正确模式 A：算术前做可表示性检查

以 `int` 加法为例：

```cpp
#include <limits>

bool add_checked(int a, int b, int& out) {
    if (b > 0 && a > std::numeric_limits<int>::max() - b) {
        return false;
    }
    if (b < 0 && a < std::numeric_limits<int>::min() - b) {
        return false;
    }
    out = a + b;
    return true;
}
```

关键点：

- 先证明结果可表示，再执行算术；
- “先算后查”在有符号场景不可接受。

---

## 7. 正确模式 B：宽类型中间值 + 显式回写检查

```cpp
#include <cstdint>
#include <limits>

bool sum_to_int(int a, int b, int& out) {
    std::int64_t t = static_cast<std::int64_t>(a) + static_cast<std::int64_t>(b);
    if (t < std::numeric_limits<int>::min() || t > std::numeric_limits<int>::max()) {
        return false;
    }
    out = static_cast<int>(t);
    return true;
}
```

该模式在工程上可读性较好，但不能省略范围校验。

---

## 8. 正确模式 C：显式模运算语义

若业务明确要求模 $2^N$ 行为：

1. 采用固定宽度无符号类型；
2. 在接口文档中声明“回绕即语义”；
3. 避免与有符号边界逻辑混写。

```cpp
#include <cstdint>

std::uint32_t step_mod32(std::uint32_t x) {
    return x + 1u; // 定义良好的 2^32 取模
}
```

注意：这不是“修复有符号溢出”，而是切换到另一种算术契约。

---

## 9. 正确模式 D：统一封装可检查算术

中大型代码库建议提供统一工具层：

- `checked_add` / `checked_sub` / `checked_mul`；
- 返回 `bool`、`std::optional<T>` 或显式错误码；
- 调用点只表达业务流程，不重复写边界细节。

好处：

1. 审计成本下降；
2. 规则一致；
3. 回归测试可复用。

---

## 10. 安全与稳定性影响

有符号溢出并非“数值误差”这么简单。

在安全敏感路径中，它可能演化为：

1. 分配长度计算错误；
2. 下标/界限校验绕过；
3. 截断链条导致协议解析失真；
4. 可被输入驱动触发的漏洞条件。

因此整型语义正确性属于安全基线的一部分。

---

## 11. 测试策略

### 11.1 边界用例优先

必须覆盖：

- `min`、`min+1`、`-1`、`0`、`1`、`max-1`、`max`。

### 11.2 性质测试

对“可检查算术”可验证：

- `ok == true` 时，与宽类型基准结果一致；
- `ok == false` 时，数学结果确实越界。

### 11.3 差分测试

对关键区间与高精度/大整数参考实现做对比。

---

## 12. CI 工具链防线

建议分层：

1. 高等级告警并将关键告警视为错误；
2. UB 与整型溢出相关 Sanitizer 覆盖测试流水线；
3. 静态分析检测可疑算术与窄化转换；
4. 对解析/协议处理等路径做 fuzz。

不要依赖单一工具；静态、动态、评审必须组合。

---

## 13. 代码评审检查单

审查算术逻辑时，逐项确认：

1. 操作数是否来自外部/不受限输入？
2. 算术前是否证明结果可表示？
3. 是否存在隐式有符号/无符号混合？
4. 是否把“有符号回绕”当作默认语义？
5. 是否存在未经验证的窄化转换？
6. 在 32/64 位目标上语义是否一致？

高危红旗：

- 先算后查；
- `abs(int)` 风格未处理 `INT_MIN`；
- 长度/容量乘法缺乏边界检查。

---

## 14. 遗留系统迁移路径

若历史代码广泛依赖隐式假设，建议：

1. 盘点热点：分配、索引、循环边界、协议长度；
2. 引入 sanitizer 构建收集问题样本；
3. 用统一 checked 工具替代分散手写算术；
4. 在可行处引入更明确的范围类型；
5. 补齐边界回归并纳入强制 CI。

优先渐进式收敛风险，避免“一次性大改”带来不可控回归。

---

## 15. 关于“性能”的正确讨论方式

有人担心边界检查带来分支开销。

建议遵循：

$$
	ext{可证明正确性} \gg \text{基于 UB 的假设性提速}
$$

先正确，再基于剖析结果做局部优化。

在多数业务系统中，错误恢复、排障和安全代价远高于几条分支指令。

---

## 16. 坏模式 / 好模式速查

| 目标 | 脆弱写法 | 稳健写法 |
|---|---|---|
| 带溢出处理的加法 | 先算后判 | 先判可表示性再算 |
| 保留数学和 | 仅用窄有符号类型 | 宽中间值 + 回写边界验证 |
| 模运算 | 假设有符号回绕 | 使用固定宽度无符号并文档化 |
| 不可信输入长度 | 直接乘法 | checked 乘法 + 失败路径 |

---

## 17. 结论回顾

1. 有符号溢出在标准 C++ 中是 UB；
2. UB 允许优化器做强假设并重写控制流；
3. “本机可运行”不是正确性证明；
4. 应采用前置边界检查、宽类型中间值、显式模语义等可验证策略；
5. 通过规则、工具、测试与评审共同约束整型语义。

整型算术必须被设计与证明，而不能凭经验猜测。
