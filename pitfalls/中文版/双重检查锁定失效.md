# 双重检查锁定失效

## 1. 问题描述

双重检查锁定（Double-Checked Locking, DCLP）常用于“懒加载单例”：

1. 先无锁检查是否已初始化；
2. 未初始化时加锁；
3. 锁内再次检查并构造对象。

这一思路看似高效，实际却是并发代码中的经典陷阱。

核心风险：

> 线程可能观察到“指针已非空，但对象状态尚未安全发布”的中间结果。

---

## 2. 讨论边界

### 2.1 本文覆盖

1. 经典 DCLP 为什么失效；
2. C++ 内存模型下的失败根因；
3. 现代 C++ 的安全替代方案；
4. 评审与迁移清单。

### 2.2 本文不覆盖

不鼓励业务代码手写复杂无锁初始化。
目标是让你优先采用标准且可证明正确的方案。

---

## 3. 典型错误写法

```cpp
MyType* g_ptr = nullptr;
std::mutex g_m;

MyType* instance_bad() {
    if (g_ptr == nullptr) {
        std::lock_guard<std::mutex> lk(g_m);
        if (g_ptr == nullptr) {
            g_ptr = new MyType();
        }
    }
    return g_ptr;
}
```

该代码常被误判为“线程安全”：

1. 双重判断避免重复构造；
2. 初始化后走无锁快路径。

但它在 C++ 语义上并不成立。

---

## 4. 失败根因：唯一性与发布性是两件事

并发初始化要同时满足两个条件：

1. **唯一性**：对象只构造一次；
2. **安全发布**：其他线程看到对象时，必须看到完整初始化状态。

经典 DCLP 常只解决唯一性，却忽略发布可见性。

---

## 5. 内存模型视角

如果共享指针读写不是正确同步的原子操作，
就会出现：

1. 指针读写竞态（data race）；
2. 构造写入与指针发布之间缺乏 happens-before。

后果是读取线程可能在“看到非空指针”时仍观察到旧状态成员值。

---

## 6. 数据竞争本身已是未定义行为

只要存在无同步的并发读写共享变量，就构成数据竞争。
在 C++ 中，数据竞争属于未定义行为（UB）。

因此，“在我的机器上没出错”不能作为正确性证明。

---

## 7. 为什么“CPU 很强顺序”不是证明

很多旧资料会引用特定架构经验（如 x86 行为）来“解释 DCLP 可用”。
这不具备可移植性，也不满足 C++ 语言级证明标准。

并发正确性必须基于：

1. 原子操作语义；
2. 同步关系（synchronizes-with）；
3. happens-before 推理链。

---

## 8. 若必须手写 DCLP 的最低条件

仅在强约束场景下才考虑手写，且必须满足：

1. 发布写入使用 `release` 语义；
2. 读取使用 `acquire` 语义；
3. 重复构造路径被锁或 CAS 严格约束；
4. 生命周期与销毁策略清晰可证明。

否则不应进入代码库。

---

## 9. 推荐替代方案一：函数内局部静态

```cpp
MyType& instance() {
    static MyType obj;
    return obj;
}
```

C++11 起，函数内局部静态初始化具备线程安全保证。

优势：

1. 代码最短；
2. 语义最清晰；
3. 无需手写内存序；
4. 通常无需动态分配。

---

## 10. 推荐替代方案二：`std::call_once`

当初始化逻辑需要拆分时，使用 `std::call_once`：

```cpp
#include <mutex>
#include <memory>

std::once_flag g_once;
std::unique_ptr<MyType> g_obj;

MyType& instance2() {
    std::call_once(g_once, [] {
        g_obj = std::make_unique<MyType>();
    });
    return *g_obj;
}
```

其语义由标准库封装，显著降低手写并发错误概率。

---

## 11. `std::call_once` 的优势

与手写 DCLP 相比：

1. 减少内存序细节错误；
2. 代码意图更清楚；
3. 评审成本更低；
4. 异常行为更可预期。

---

## 12. 初始化异常语义

`std::call_once` 的可调用对象若抛异常，
`once_flag` 不会永久置位，后续调用会重试。

函数内局部静态在初始化失败后同样允许后续重试。
这类行为应在接口文档中写明。

---

## 13. 生命周期与销毁策略

初始化正确并不代表整体设计正确。
还需明确：

1. 对象是否进程全程存活；
2. 是否需要可控销毁；
3. 退出阶段是否存在依赖关系。

很多线上问题出在“析构顺序”，而非“初始化竞态”。

---

## 14. 反初始化顺序风险

即便初始化安全，静态对象跨翻译单元析构顺序仍可能不确定。
若 A 的析构依赖 B，但 B 已析构，仍会触发故障。

常见缓解：

1. 避免静态对象之间隐式依赖；
2. 显式 shutdown 流程；
3. 必要时采用进程生命周期对象。

---

## 15. 性能误区

“手写 DCLP 一定更快”通常缺乏实测支持。
在多数业务场景中，局部静态或 `call_once` 的后续开销非常小。

实践顺序应是：

1. 先保证正确性；
2. 再做真实负载测量；
3. 最后决定是否需要更低层方案。

---

## 16. 何时需要更底层原子方案

极少数基础设施层场景可能需要自定义无锁发布。
此时必须提供书面证明：

1. 精确内存序选择；
2. happens-before 证明链；
3. 生命周期/回收策略；
4. 销毁阶段安全性。

没有证明的“并发技巧”不应合并。

---

## 17. 高频反模式

1. 锁外非原子读 + 锁内非原子写；
2. 用 `relaxed` 做对象发布信号；
3. 依赖特定 CPU 行为；
4. 多路径初始化缺乏唯一所有权；
5. 忽略退出阶段依赖。

---

## 18. 快速审查问题

评审懒加载代码时可先问：

1. 是否存在任何共享变量竞态读写？
2. 发布可见性是否有 acquire-release 证明？
3. 是否可能重复构造？
4. 销毁策略是否明确？
5. 是否可替换为局部静态或 `call_once`？

若回答不清晰，应拒绝当前实现。

---

## 19. 代码评审清单

- [ ] 优先使用函数内局部静态。
- [ ] 需要分离初始化时优先 `std::call_once`。
- [ ] 禁止无必要手写 DCLP。
- [ ] 若手写原子路径，需提供可审计的同步证明。
- [ ] 初始化失败语义明确。
- [ ] 销毁/退出顺序语义明确。

---

## 20. 旧代码迁移建议

迁移步骤：

1. 扫描并定位手写 DCLP；
2. 能替换为局部静态的优先替换；
3. 其余替换为 `std::call_once`；
4. 增加并发压力测试与工具检测；
5. 文档化生命周期与析构策略。

通常能同时提升可维护性与可靠性。

---

## 21. 总结

双重检查锁定之所以危险，在于其“外观正确”但常违反内存模型要求。

工程结论：

1. 默认使用 C++11+ 线程安全局部静态；
2. 结构需要时使用 `std::call_once`；
3. 避免手写 DCLP，除非能给出完整同步与生命周期证明。

并发正确性必须建立在语言级 happens-before 推理上，
而不是经验、直觉或平台偶然性。
