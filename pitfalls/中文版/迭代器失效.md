# 迭代器失效（Iterator Invalidation）

## 1. 问题描述

在 C++ 容器中，迭代器、引用和指针的有效性依赖容器结构状态。
当容器发生插入、删除、扩容、rehash 等修改时，
这些“句柄”可能失效。

继续使用失效句柄属于未定义行为（UB）。

该问题常见且隐蔽：

1. 代码可编译；
2. 小样本测试可能通过；
3. 生产环境在特定数据规模或时序下崩溃。

---

## 2. 讨论边界

### 2.1 本文覆盖

1. 迭代器失效根因；
2. 不同容器家族的典型失效模式；
3. 安全遍历与修改模式；
4. 评审与迁移清单。

### 2.2 本文不覆盖

不完整复刻标准中每个操作的全部条目。
重点是高频场景与工程可执行规则。

---

## 3. 最小示例

```cpp
#include <vector>

std::vector<int> v{1, 2, 3};
auto it = v.begin();
v.push_back(4); // 可能触发重分配
int x = *it;    // 若重分配则 UB
```

当 `push_back` 触发重分配时，旧内存失效，`it` 不再可用。

---

## 4. 失效根因

容器修改可能导致：

1. 元素搬迁到新内存；
2. 元素相对位置变化；
3. 节点被删除；
4. 哈希桶重建（rehash）。

句柄若依赖旧拓扑或旧地址，即可能失效。

---

## 5. 不只迭代器会失效

同类风险对象包括：

1. 指向元素的引用；
2. 指向元素的裸指针；
3. 从容器数据派生的 view/span/string_view。

审查时不能只盯 `iterator`。

---

## 6. 容器家族的典型失效特征

### 6.1 连续存储容器（`vector` / `string`）

典型特征：

1. 重分配可使所有句柄失效；
2. 插入/删除会使受影响位置及其后句柄失效；
3. `reserve` 只降低重分配概率，不是绝对安全保证。

### 6.2 `deque`

分段存储，规则更细。
某些操作可能使迭代器大范围失效，
但引用规则又可能不同。

不确定时应按“高风险”处理。

### 6.3 节点型容器（`list` / `forward_list`）

插入通常不使已有迭代器失效；
删除只使被删节点相关句柄失效。

稳定性更好，但性能模型不同。

### 6.4 关联容器与无序容器

`map`/`set` 常具较稳定迭代器语义（除被删元素）。

`unordered_*` 在 rehash 时可使迭代器失效。
引用与指针规则可能与迭代器不同，需分别确认。

---

## 7. 高频错误模式

### 7.1 迭代时缓存 `end`

```cpp
for (auto it = v.begin(), e = v.end(); it != e; ++it) {
	v.push_back(*it); // e 可能失效
}
```

对会结构变化的容器，该写法高风险。

### 7.2 `erase` 后继续 `++it`

```cpp
for (auto it = v.begin(); it != v.end(); ++it) {
	if (pred(*it)) {
		v.erase(it); // it 已失效
	}
}
```

应使用 `erase` 返回值更新迭代器。

### 7.3 跨扩容保存元素地址

```cpp
int* p = &v[0];
v.push_back(42);
use(*p); // 可能悬垂
```

---

## 8. 正确删除循环模板

```cpp
for (auto it = v.begin(); it != v.end(); ) {
	if (pred(*it)) {
		it = v.erase(it); // 获取下一个有效迭代器
	} else {
		++it;
	}
}
```

该模板应作为团队约定写法。

---

## 9. `reserve` 的作用边界

`reserve` 可以降低扩容频率，但不能消除所有失效风险。

它是性能与概率优化手段，
不是“句柄永久稳定”的正确性保证。

---

## 10. 可能失效后必须重新获取

工程规则：

1. 凡是可能失效的修改操作后，
2. 迭代器/引用/指针都应重新获取。

不要依赖“这次恰好没失效”。

---

## 11. 索引遍历并非银弹

对连续容器，索引遍历有时更直观：

```cpp
for (std::size_t i = 0; i < v.size(); ++i) {
	// 若容器变长/删元素，语义仍需谨慎
}
```

索引可减少部分迭代器问题，但仍需处理元素位移与长度变化。

---

## 12. `erase-remove` 模式

批量按条件删除推荐：

```cpp
v.erase(std::remove_if(v.begin(), v.end(), pred), v.end());
```

C++20 可用 `std::erase_if(v, pred)`，
可显著减少手写迭代器错误。

---

## 13. range-for 中修改容器风险

对同一容器 range-for 时做结构修改通常危险：

```cpp
for (auto& x : v) {
	if (x == 1) v.push_back(2);
}
```

除非你能证明该容器与操作组合下句柄稳定，否则应避免。

---

## 14. 无序容器的 rehash 陷阱

`unordered_map` / `unordered_set` 在桶重建时常使迭代器失效。

建议：

1. 预留桶容量；
2. 插入密集期避免长期持有迭代器；
3. rehash 可能发生后重新获取句柄。

---

## 15. 借用视图同样受影响

若 `span`/`string_view` 来自容器内部存储，
容器结构修改后视图也可能失效。

“我没用 iterator，所以安全”是错误认知。

---

## 16. 并发场景下风险更高

并发修改与遍历若无同步，会同时触发：

1. 数据竞争；
2. 句柄失效；
3. 容器不变式破坏。

并发安全与失效安全是两套约束，缺一不可。

---

## 17. 容器选择与稳定性权衡

连续容器：

- 优势：缓存友好；
- 劣势：结构修改时句柄稳定性弱。

节点容器：

- 优势：迭代器稳定性强；
- 劣势：局部性与分配成本可能更差。

应根据实际读写模式选择容器。

---

## 18. API 设计建议

若 API 暴露内部容器迭代器/引用，
必须文档化其失效条件。

更稳健做法：

1. 返回值快照；
2. 返回稳定 ID；
3. 减少外部对内部迭代器稳定性的依赖。

---

## 19. 常见反模式

1. 长期保存迭代器作为对象成员；
2. 跨扩容保存 `vector` 元素地址；
3. 回调中修改当前遍历容器；
4. 假设所有 STL 容器失效规则相同；
5. 用“测试没挂”替代语义证明。

---

## 20. 更安全的修改模式

1. 阶段分离：先收集，后修改；
2. 修改后重取句柄；
3. 使用标准返回迭代器模式；
4. 缩小可变区间和句柄作用域。

这能显著降低认知复杂度。

---

## 21. 旧代码治理路径

1. 检索长期持有迭代器/引用字段；
2. 审查“遍历中修改”循环；
3. 替换为标准安全模板；
4. 补充 rehash/扩容压力测试；
5. 将容器规则写入模块文档。

---

## 22. 工具辅助

可使用：

1. ASan/UBSan（运行期问题信号）；
2. STL debug iterator 模式（工具链支持时）；
3. 静态分析规则（可疑失效模式告警）。

工具可提早发现问题，但无法替代规则理解。

---

## 23. 代码评审清单

- [ ] 是否在修改后继续使用旧句柄？
- [ ] 当前操作对应容器失效规则是否明确？
- [ ] `erase` 循环是否使用返回迭代器？
- [ ] 是否存在源于容器存储的 view/span 被跨修改使用？
- [ ] rehash/扩容是否可能打破假设？
- [ ] 迭代与修改协议是否文档化？

任何一项不明确，都应先重构。

---

## 24. 规避策略汇总

1. 按容器与操作学习失效规则；
2. 可能失效后立即重取句柄；
3. 使用标准安全循环模板；
4. 按稳定性需求选容器；
5. 将失效前置条件写进 API 合同。

---

## 25. 总结

迭代器失效不是边角知识，而是容器编程的核心正确性约束。

稳健 C++ 代码应将“句柄有效性”视为一等合同：

1. 结构变更即重新评估句柄；
2. 规则不清就不继续使用旧句柄；
3. 通过模板化写法与评审清单降低人为错误。

当团队形成这一共识后，可系统性消除一大类隐蔽 UB 问题。
