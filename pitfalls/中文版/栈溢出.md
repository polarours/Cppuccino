# 栈溢出

## 引言

调用栈是一块有限的内存区域。每次函数调用都会压入一个**栈帧**（返回地址、保存的寄存器、局部变量）。所谓**栈溢出**，就是存活栈帧的总大小超出了栈的上限——最常见于无界或过度深的递归，也可能是因为在栈上按值分配了过大的对象。

与内存泄漏不同，栈溢出通常很「吵」：程序当场被终止（Linux 上即 SIGSEGV）。但它依然是必须从源头设计掉的真实缺陷。

## 问题

```cpp
// 没有基准情形：这个函数会一直递归，直到栈被耗尽。
void countdown() {
    countdown();   // 每次调用都增加一个栈帧；栈最终会耗尽
}
```

一个更隐蔽、也很常见的情形是，对**大输入而言合法但很深**的递归：

```cpp
// 递归计算 a[i..n) 的和。
long long sum(const std::vector<long long>& a, size_t i) {
    if (i == a.size()) return 0;
    return a[i] + sum(a, i + 1);   // 深度 == a.size()；对大 vector 会溢出
}
```

**为什么出错：**
- `countdown()` 没有终止条件，于是永远压栈，直到操作系统杀掉线程——必崩。
- `sum()` 对小 vector 正常，可一旦 `a.size()` 超过几万帧（典型栈大小为 8 MiB）就会栈溢出。这个 bug 只在「大」的真实输入下才出现，于是它溜过了小单元测试。
- 在栈上按值分配大对象，例如函数内 `char buffer[1 << 20];`（1 MiB），也可能在一帧内直接撑爆栈。

## 修复

优先采用**迭代**写法，把状态从栈上移到循环或堆分配的结构里：

```cpp
#include <vector>

long long sum(const std::vector<long long>& a) {
    long long total = 0;
    for (size_t i = 0; i < a.size(); ++i) {   // 状态在循环里，不在栈上
        total += a[i];
    }
    return total;
}
```

当递归确实能刻画问题（树遍历、分治）时，你可以：
- **改用显式栈**（堆上的 `std::vector` 或 `std::deque`），用循环自己管理，这样深度只受可用堆大小限制；或
- **保留尾递归**并依赖编译器尾调用优化成循环（用 `-O2` 配合工具/检查确认——C++ 不保证一定优化）；或
- **仅作为最后手段增大栈大小**（例如 `ulimit -s` / `pthread_attr_setstacksize`），仅适用于确实很深但有界的递归。

同时避免巨型按值局部变量；用 `std::vector<char>`（堆支持）替代大数组。

## 最佳实践

- **递归需要基准情形 *且* 深度可被证明有界。** 「它能终止」还不够；对你的**最大预期输入**，深度必须装得下栈。
- **把深的线性递归换成循环。** 求和、拷贝、在扁平区间里查找——这些用迭代几乎总是更清晰更安全。
- **对树/图递归，当深度可能很大时考虑显式（堆）工作栈**（例如一个退化的、伪装成树的链表）。
- **警惕大栈分配。** 几兆字节的局部数组或 `std::array` 是「一帧即溢出」的隐患；把大缓冲区放到堆上。
- **让编译器警告你。** 用 `-Wstack-usage=<bytes>` 构建，当某个函数的栈用量可能超出预算时给出诊断。

## 总结

栈溢出是栈在告诉你：它已经没有空间容纳更多调用帧了。修复办法很少是「把栈调大」；而是**停止压入无界的栈帧**：把深层的、开放式的递归改写成迭代或显式堆支持的栈，并把大对象移出栈。要按**最大**输入来设计，而不只是按测试套件里的那个输入。
