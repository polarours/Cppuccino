# 优先级反转

## 1. 引言

**优先级反转（priority inversion）** 是实时系统和基于优先级调度的系统中一种调度异常。一个高优先级线程被阻塞，等待低优先级线程持有的资源；与此同时，一个*中*优先级线程——它根本不需要这个资源——却运行起来并抢占了低优先级线程。结果就是：高优先级线程被中优先级线程间接地阻塞了。

它因为导致火星探路者（Mars Pathfinder）看门狗定时器误触发重启而"名声大噪"。

## 2. 问题

三个线程，优先级 High > Medium > Low：

```cpp
#include <mutex>
#include <thread>

std::mutex resource;

void low_priority() {
    std::lock_guard<std::mutex> lock(resource);
    do_work();   // 持有锁期间做工作
}               // 中优先级线程可能在这里抢占 Low

void medium_priority() {
    // 不使用 resource，但一直占着 CPU 忙等
    busy_loop();
}

void high_priority() {
    std::lock_guard<std::mutex> lock(resource);  // 阻塞：Low 仍持有它
    use_resource();
}
```

### 为什么出错

1. Low 拿到 `resource`。
2. High 启动，尝试锁 `resource`，被阻塞（等待 Low）。
3. Medium 变为可运行，并抢占 Low（Medium 优先级高于 Low），于是 Low 无法完成它的临界区。
4. High 现在实际上被 Medium 阻塞了——优先级顺序被反转了。

在严格的优先级调度下，High 会等待任意长的时间，因为 Medium 一直在跑，Low 拿不到 CPU 去释放那把锁。

## 3. 修复

### 3.1 优先级继承（操作系统 / pthread 层面）

大多数实时操作系统，以及配置了 `PTHREAD_PRIO_INHERIT` 的 `pthread` 互斥锁，都实现了**优先级继承**：当 Low 持有 High 正在等待的锁时，Low 会临时"继承"High 的优先级，从而能尽快完成并释放锁。

```cpp
// POSIX 示例
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&mutex, &attr);
```

### 3.2 缩短临界区时间

把锁持有时间压到最短；把繁重的计算放到锁*外*去做，让 Low 尽快释放 `resource`。

### 3.3 在优先级敏感的路径上避免使用共享锁

改用无锁结构或每线程所有权，从根上消除引发反转的那把共享互斥锁。

## 4. 最佳实践

1. **在 RTOS / pthread 环境用优先级继承互斥锁**。
2. **高优先级线程的临界区要极小**。
3. **隔离优先级域**，让中优先级线程无法抢占锁的持有者。
4. **用模拟负载测试**，以暴露由反转引发的延迟尖刺。

## 5. 总结

- 优先级反转：High 被 Medium 阻塞，因为 Low 持有那把锁。
- 成因是优先级调度 + 共享互斥锁 + 可抢占的中优先级线程。
- 通过优先级继承、缩短临界区，或无锁设计来修复。
- 实时系统中一类典型的"神秘延迟"来源。
