# `std::string_view` 悬垂问题

## 1. 问题描述

`std::string_view` 是轻量、非拥有（non-owning）的字符串视图。
它能减少拷贝与分配，是现代 C++ 常用工具。

但它的核心风险也非常直接：

> `string_view` 不拥有底层内存，也不会延长底层对象生命周期。

一旦底层字符缓冲区销毁、重分配或超出约束范围，
视图就可能悬垂或语义失效。

这类问题在代码审查中很容易被忽略，因为接口看起来“高效且优雅”。

---

## 2. 讨论边界

### 2.1 本文覆盖

1. `string_view` 悬垂的根因；
2. 高频错误模式；
3. API 设计与生命周期合同策略；
4. 迁移与评审清单。

### 2.2 本文不覆盖

本文并非否定 `string_view`。
当生命周期可证明时，它是非常优秀的抽象。

---

## 3. 最小错误示例

```cpp
#include <string>
#include <string_view>

std::string_view bad() {
    return std::string("temporary"); // 指向临时对象
}
```

返回后临时 `std::string` 已销毁，
视图指针与长度都失去意义，访问即未定义行为。

---

## 4. 根因机制

`string_view` 通常持有：

1. 指向字符序列的指针；
2. 序列长度。

它不持有所有权 token。
生命周期完全由外部对象决定。

因此，若外部对象先销毁：

1. 指针悬垂；
2. 长度成为失效元数据；
3. 读取行为不再受语言保证。

---

## 5. 借用语义（Borrowing）必须显式

将 `string_view` 视为“借用引用”，而不是“轻量字符串值”。

借用基本规则：

> 被借用对象寿命必须覆盖借用者使用区间。

若无法证明该关系，应改为拥有型 `std::string`。

---

## 6. 高频失效模式

### 6.1 返回局部字符串视图

```cpp
std::string_view f() {
    std::string s = "abc";
    return s; // 悬垂
}
```

### 6.2 返回临时表达式视图

```cpp
std::string_view g() {
    return std::string("x") + "y"; // 临时对象销毁
}
```

### 6.3 存储到长生命周期对象

```cpp
struct Holder {
    std::string_view v;
};

Holder make_holder() {
    std::string tmp = "abc";
    return Holder{tmp}; // v 悬垂
}
```

### 6.4 异步路径跨边界传递

`string_view` 被捕获并延后执行，原始字符串已结束生命周期。

### 6.5 原字符串变更导致视图失效

底层 `std::string` 重分配后，旧 view 可能失效。

---

## 7. “本地没崩”不是正确性证明

悬垂问题常在 Debug 环境不复现，
但在优化构建、不同分配器、不同时序下爆发。

并发或异步场景会显著放大这种不确定性。

正确性必须来自生命周期推理。

---

## 8. 失效类型区分

### 8.1 生命周期失效

底层存储不存在，访问是 UB。

### 8.2 语义失效

底层存储还在，但内容/长度假设已不成立。
例如 owner 被修改后，view 仍沿用旧语义。

两者都危险，第一类更致命。

---

## 9. 返回类型策略

若返回值需要跨作用域持有，优先返回 `std::string`：

```cpp
std::string make_name() {
    return "name";
}
```

只有当返回视图确实绑定到长期稳定存储时，才返回 `string_view`。

---

## 10. 参数层面的安全用法

`string_view` 作为只读参数通常非常合适，当且仅当：

1. 函数不保存该 view；
2. 使用范围严格在调用期间；
3. 生命周期要求对调用者明确。

```cpp
void log_line(std::string_view msg);
```

---

## 11. 成员存储风险

长期对象中存储 `string_view` 是高风险设计。

除非类型本身就是“借用视图类型”，
否则默认成员应使用 `std::string`。

存 view 时必须在接口契约中明确所有者与寿命关系。

---

## 12. API 文档模板（建议固定）

任何涉及 `string_view` 的公开 API，建议文档明确：

1. 参数/返回值是借用还是拥有；
2. 底层存储寿命要求；
3. 是否会内部缓存 view；
4. 异步或跨线程行为约束。

合同不写清，误用几乎必然发生。

---

## 13. `substr` 链式视图注意点

`string_view::substr` 返回的仍是视图，不分配新存储。
它不会改变原始生命周期约束。

派生 view 的安全性仍完全依赖原始 owner 存活。

---

## 14. 与 `std::string` 变更操作的关系

若 view 指向某个 `std::string`，
而该字符串后续发生可能重分配的修改，view 可能失效。

工程策略：

1. view 使用期间冻结 owner；或
2. owner 变更后重新获取 view。

---

## 15. 并发语境

`string_view` 拷贝很便宜，但底层数据不是拷贝。
若其他线程销毁或修改 owner，消费者线程视图可能瞬间失效。

同步责任在 owner 生命周期管理，不在 `string_view` 本身。

---

## 16. 异步边界策略

跨线程队列、任务系统、回调缓存等边界，
默认应把借用数据转换为拥有数据：

```cpp
void enqueue(std::string s);

void enqueue_view(std::string_view sv) {
    enqueue(std::string(sv));
}
```

这会有一次拷贝成本，但能换来可证明正确性。

---

## 17. 性能与安全权衡

`string_view` 的性能收益是真实的，
但悬垂缺陷的代价通常远高于一次合理拷贝。

正确流程：

1. 先建立安全生命周期边界；
2. 再做基准测试；
3. 再局部优化高频路径。

---

## 18. 工具与检测

可辅助发现问题的工具：

1. 编译器相关警告（返回临时引用/视图）；
2. 静态分析器（逃逸生命周期推理）；
3. AddressSanitizer（部分 UAF 报告）。

注意：工具不能替代 API 生命周期合同。

---

## 19. 典型反模式

1. 返回由临时 `std::string` 构造的 `string_view`；
2. 将参数 `string_view` 直接存为成员；
3. 异步任务中传播借用 view；
4. 将 view 作为长期容器 key 但底层数据可变；
5. 把字符串字面量寿命与临时对象寿命混为一谈。

---

## 20. 旧代码治理建议

1. 检索所有 `string_view` 返回类型；
2. 审查 `string_view` 成员字段；
3. 为 API 标注借用/拥有语义；
4. 在高风险路径改为 `std::string`；
5. 增加异步和变更场景测试。

---

## 21. 代码评审清单

- [ ] 该 view 是否可能超过底层存储寿命？
- [ ] 返回 view 是否绑定到稳定存储？
- [ ] 成员 view 是否有明确生命周期合同？
- [ ] 异步边界是否转为拥有数据？
- [ ] owner 变更是否可能使活动 view 失效？
- [ ] 文档是否明确前置条件？

任一项不确定时，优先改为拥有语义。

---

## 22. 实务建议汇总

1. 跨作用域返回默认 `std::string`；
2. `string_view` 优先用于“只读且不存储”的参数；
3. 存储 view 前必须先写清借用合同；
4. 异步边界优先做拥有化转换；
5. 生命周期假设必须在 API 层显式化。

---

## 23. 总结

`std::string_view` 的价值在于零拷贝视图能力，
其风险也来自同一特性：不拥有内存。

工程准则可以概括为：

> 生命周期可证明时用 `string_view`；
> 生命周期不明确时用 `std::string`。

先保证正确性，再追求优化。
这是避免 `string_view` 悬垂问题的唯一稳健路径。
