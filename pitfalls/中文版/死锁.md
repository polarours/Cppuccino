# 死锁

## 1. 引言

**死锁（deadlock）** 是指两个或更多线程永久阻塞，每个线程都在等待环中另一个线程持有的资源（通常是锁）。谁都无法继续，程序就此卡死。

死锁必须同时满足 **Coffman 四条件**：

1. **互斥（Mutual exclusion）**——一个资源同一时间只能被一个线程持有。
2. **持有并等待（Hold and wait）**——线程在持有一个资源的同时等待另一个资源。
3. **不可抢占（No preemption）**——已持有的资源不能被强行夺走。
4. **循环等待（Circular wait）**——线程形成一条互相等待的环。

只要打破其中任意一个条件，死锁就不会发生。

## 2. 问题

```cpp
#include <mutex>
#include <thread>

std::mutex mtx_a;
std::mutex mtx_b;

void thread_one() {
    std::lock_guard<std::mutex> la(mtx_a);
    // ... 持有 mtx_a 时做一些工作 ...
    std::lock_guard<std::mutex> lb(mtx_b);  // 等待 mtx_b
    // 使用两个资源
}

void thread_two() {
    std::lock_guard<std::mutex> lb(mtx_b);   // 注意锁的顺序相反
    // ... 持有 mtx_b 时做一些工作 ...
    std::lock_guard<std::mutex> la(mtx_a);   // 等待 mtx_a
    // 使用两个资源
}
```

### 为什么出错

如果 `thread_one` 拿到了 `mtx_a`，而 `thread_two` 拿到了 `mtx_b`，那么两个线程都会永远阻塞在对方的锁上——形成循环等待。这就是经典的**锁顺序**死锁。这个 bug 很隐蔽，因为它只在时机不巧时发生，而不是每次运行都出现。

## 3. 修复

### 3.1 始终按一致的全局顺序加锁

如果代码里每个线程都先拿 `mtx_a` 再拿 `mtx_b`，就不会形成环。这方法简单，但随着项目变大很容易被违反。

### 3.2 用 `std::lock` / `std::scoped_lock`（C++17）一次性原子加锁

```cpp
#include <mutex>

std::mutex mtx_a;
std::mutex mtx_b;

void safe_transfer() {
    // 无论调用顺序如何，都以保证不死锁的方式同时获取两把锁
    std::scoped_lock lock(mtx_a, mtx_b);
    // 使用两个资源
}
```

`std::scoped_lock`（以及更底层的 `std::lock`）会用一套成熟的算法同时获取所有参数，保证不死锁，你不必再手动纠结加锁顺序。

## 4. 最佳实践

1. **获取多把锁时用 `std::scoped_lock`**，而不是嵌套的 `lock_guard`。
2. **缩小临界区**，减少锁的持有时间。
3. **持有锁时不要调用来路不明的代码**——它可能会再去拿另一把锁，形成环。
4. **考虑无锁或单所有者设计**，从根上消除问题。
5. **用工具检测**——ThreadSanitizer 能报告潜在的死锁。

## 5. 总结

- 死锁需要 Coffman 四条件同时成立；打破任意一个即可避免。
- 最常见的原因是**锁顺序不一致**。
- `std::scoped_lock` / `std::lock` 以不死锁的方式获取多把互斥锁。
- 最小化持锁、避免重入式加锁。
