# Lambda 捕获悬垂引用

## 1. 问题描述

Lambda 可以按值捕获，也可以按引用捕获。
当 lambda 通过引用捕获对象，并在该对象生命周期结束后仍被调用时，
闭包中保存的引用将变为悬垂引用。

这属于未定义行为（UB），常表现为：

1. 偶发崩溃；
2. 数据异常；
3. 在不同优化级别下行为不一致。

其危险在于：代码表面上“很正常”，甚至在本地测试中长期不复现。

---

## 2. 讨论边界

### 2.1 本文覆盖

1. 为什么悬垂捕获会发生；
2. 典型触发场景；
3. 异步/线程环境下风险放大机制；
4. 安全捕获与所有权策略；
5. 评审与迁移清单。

### 2.2 本文不覆盖

不否定 lambda 本身。
本文目标是建立严格生命周期推理，而非限制语法使用。

---

## 3. 最小失败示例

```cpp
#include <functional>

std::function<int()> make_bad() {
    int x = 7;
    return [&]() { return x; }; // 引用捕获 x
}
```

`make_bad` 返回后，局部变量 `x` 已销毁。
后续调用该函数对象读取到悬垂引用，行为未定义。

---

## 4. 根因机制

lambda 闭包对象会保存捕获状态：

- 按值捕获：闭包成员持有值副本；
- 按引用捕获：闭包成员绑定外部对象引用。

如果外部对象先于闭包调用消亡，引用失效。
语言不会自动帮你延长被引用对象寿命。

---

## 5. “能跑”不等于正确

这类 UB 在 Debug 环境常“看起来没问题”。
但在以下条件变化时容易爆发：

1. 优化级别提升；
2. 栈布局变化；
3. 调度时序变化；
4. 编译器版本更换。

正确性必须由生命周期规则证明，而非经验观察。

---

## 6. 高频触发场景

### 6.1 返回 lambda

函数返回捕获局部引用的 lambda。

### 6.2 存入长生命周期容器

lambda 被保存到成员变量、全局回调表、事件总线、任务队列。

### 6.3 异步执行

提交到线程池、定时器、协程 continuation，执行时间晚于捕获作用域。

### 6.4 分离线程

在 detached 线程中引用捕获局部对象，风险极高。

---

## 7. 安全基线：逃逸 lambda 默认值捕获

```cpp
#include <functional>

std::function<int()> make_good() {
    int x = 7;
    return [x]() { return x; }; // 值捕获
}
```

闭包拥有 `x` 的副本，生命周期独立于原作用域。

---

## 8. 捕获默认方式的风险

### 8.1 `[&]`

默认按引用捕获所有被使用变量。
在逃逸场景中非常危险。

### 8.2 `[=]`

默认按值捕获，通常更安全，但可能产生额外拷贝。

### 8.3 建议

在非平凡代码中避免宽泛默认捕获，
优先显式写出捕获列表，表达所有权意图。

---

## 9. `this` 捕获陷阱

捕获 `this` 只是复制指针值，不会复制对象。
若对象先析构，lambda 中 `this` 立刻悬垂。

风险示例：

```cpp
class Worker {
public:
    void schedule();
private:
    int value_ = 0;
};

void Worker::schedule() {
    submit([this] { use(value_); }); // 若对象提前销毁则 UB
}
```

---

## 10. `this` 的安全策略

### 10.1 捕获快照

只需读取快照时：

```cpp
submit([v = value_] { use(v); });
```

### 10.2 显式共享所有权

```cpp
class Worker : public std::enable_shared_from_this<Worker> {
public:
    void schedule() {
        auto self = shared_from_this();
        submit([self] { self->do_work(); });
    }
    void do_work();
};
```

该方案会改变生命周期图，应评估循环引用与资源保留问题。

---

## 11. `std::reference_wrapper` 不是寿命延长器

`std::ref` 只是显式引用语义包装，不延长对象生命周期。
原对象销毁后，wrapper 同样悬垂。

仅在外部已能证明寿命覆盖时使用。

---

## 12. 移动捕获（init-capture）

对于需要转移所有权到闭包的场景：

```cpp
auto fn = [p = std::move(ptr)]() {
    if (p) use(*p);
};
```

这是处理逃逸 lambda 的可靠方式。

---

## 13. 异步环境的风险放大

异步框架常把执行延后到未来时刻，且可能跨线程。
这会放大生命周期错配窗口。

“这个回调通常马上执行”不应作为安全前提，
除非 API 文档明确保证同步调用。

---

## 14. 事件系统与延迟队列

在事件驱动架构中，回调通常会被缓存并延迟触发。
此时应默认：

1. 数据按值捕获；
2. 对象通过 shared/weak 明确所有权；
3. 禁止隐式引用捕获默认。

---

## 15. weak 模式回调

避免“无限延寿”可用 weak 方案：

```cpp
auto weak = weak_from_this();
submit([weak] {
    if (auto self = weak.lock()) {
        self->do_work();
    }
});
```

该模式可同时避免悬垂与强制存活。

---

## 16. 协程场景

协程 continuation 经常跨挂起点保存闭包状态。
若使用引用捕获且恢复发生在原作用域之后，风险极高。

协程中的逃逸闭包应优先值捕获或显式所有权。

---

## 17. 性能与安全权衡

值捕获可能带来拷贝成本，但多数情况下成本可接受。
正确策略是：

1. 先保证生命周期安全；
2. 再做性能测量；
3. 再用移动捕获/共享不可变状态优化。

不要用引用捕获“赌正确性”换微小性能收益。

---

## 18. 检测手段

推荐工具组合：

1. AddressSanitizer（UAF 检测）；
2. UBSan（UB 信号）；
3. ThreadSanitizer（并发相关问题）；
4. 静态分析（逃逸引用捕获告警）。

单一工具不足以覆盖全部生命周期缺陷。

---

## 19. 代码异味（Code Smells）

1. 逃逸回调使用 `[&]`；
2. 回调跨线程/跨时序却引用捕获局部变量；
3. 成员异步回调直接捕获裸 `this`；
4. 默认捕获掩盖所有权语义；
5. 生命周期假设仅写在注释中。

---

## 20. 安全设计准则

1. 逃逸 lambda 默认值捕获；
2. 对象回调明确选择 shared 或 weak 策略；
3. 捕获列表显式且最小化；
4. 能快照就快照，减少共享可变状态；
5. 在 API 文档中写清回调生命周期合同。

---

## 21. API 合同示例

回调型 API 至少应说明：

1. 回调是否异步执行；
2. 回调是否可能在调用点返回后触发；
3. 参数引用寿命要求；
4. 线程/执行器上下文。

明确合同能显著降低误用概率。

---

## 22. 评审清单

- [ ] 该 lambda 是否会逃逸当前作用域？
- [ ] 逃逸路径中是否存在引用捕获？
- [ ] 是否在异步路径捕获了裸 `this`？
- [ ] 所有权模型是否显式（值 / shared / weak）？
- [ ] 是否避免了宽泛默认捕获？
- [ ] 生命周期假设是否文档化？

若任一项不清晰，应优先重构。

---

## 23. 旧代码迁移建议

可按步骤治理：

1. 在回调密集模块检索 `[&]`；
2. 区分逃逸与非逃逸 lambda；
3. 逃逸场景改为值捕获/显式所有权；
4. 引入 weak 回调模式；
5. 用 Sanitizer + 压测验证。

该治理通常能消除一类最难定位的线上偶发问题。

---

## 24. 总结

Lambda 捕获悬垂引用本质上是“生命周期合同缺失”。
它不复杂，但危害大、复现难、定位成本高。

实务基线：

1. 逃逸即默认不引用捕获；
2. 异步回调必须显式所有权策略；
3. `this` 捕获按指针生命周期问题处理；
4. 评审与工具双重护栏。

当捕获语义与生命周期被显式化，lambda 才是可靠的抽象。
当它们依赖隐含假设，风险几乎不可避免。
