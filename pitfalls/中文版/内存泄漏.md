# 内存泄漏

## 引言

所谓**内存泄漏**，就是程序分配了内存却再也无法释放它。在 C++ 里，泄漏几乎总是同一个根本原因的症状：**用手动管理所有权（裸指针）代替了让类型系统替你管理**。

现代 C++ 提供了 `std::unique_ptr`、`std::shared_ptr`、容器等工具，能让你从「构造层面」几乎杜绝泄漏。然而泄漏仍是最常见的问题之一，尤其在仍手写 `new`/`delete` 的代码库里。

## 问题

```cpp
#include <string>

struct Record {
    std::string name;
    int value;
};

void process(bool skip) {
    Record* r = new Record{"alpha", 1};   // (1) 所有权从这里开始

    if (skip) {
        return;                            // (2) 泄漏：r 永远不会被 delete
    }

    // ... 中间可能抛出异常的工作 ...

    delete r;                             // (3) 只有走这条路才会释放
}
```

**为什么出错：**
- 若 `skip` 为 `true`，函数在 (2) 提前返回，`r` 从未被释放——每次这样的调用都泄漏。
- 若 (1) 到 (3) 之间的任何代码抛出异常，控制流离开函数时不会执行 `delete`——错误路径上也会泄漏。
- 泄漏是「安静」的：程序继续运行，慢慢吃掉内存，直到被 OOM killer 杀掉或卡死。`new` 不会因为「你忘了释放」而报错；它只会在**整个系统**内存耗尽时抛出 `std::bad_alloc`。
- 即便「正常路径」也很脆弱：每新增一个提前 return 或异常点，就多一处潜在的泄漏源。

## 修复

使用 `std::unique_ptr`，把析构绑定到作用域，而不是手写 `delete`：

```cpp
#include <memory>
#include <string>

struct Record {
    std::string name;
    int value;
};

void process(bool skip) {
    auto r = std::make_unique<Record>(Record{"alpha", 1});  // 拥有该对象

    if (skip) {
        return;                            // OK：此处 r 被析构，内存已释放
    }

    // ... 若此处抛出异常，栈会展开，r 被自动析构 ...

}   // 无论以何种方式离开函数，r 都会在此处析构 -> 永不泄漏
```

若所有权需要在函数间共享或转移，使用 `std::shared_ptr` 或移动 `std::unique_ptr`：

```cpp
std::unique_ptr<Record> load() {
    return std::make_unique<Record>(Record{"beta", 2});   // 所有权转移出去
}

void use(std::unique_ptr<Record> r) { /* 拥有它；返回即释放 */ }
```

当资源**不是**内存（文件句柄、套接字、锁）时，写一个小的 RAII 包装器或使用现成的（`std::lock_guard`、`std::fstream`）：同样的「析构即释放」规则适用。

## 最佳实践

- **不要在应用代码里手写裸 `new`/`delete`。** 如果觉得需要，几乎总有 `std::make_unique` / `std::make_shared` 可以替代。
- **每个资源只有一个所有者。** `std::unique_ptr` 表达单一所有权；`std::shared_ptr` 表达带清晰引用计数的共享所有权。裸指针只应**观察**，绝不应拥有。
- **让容器拥有其元素。** 用 `std::vector<Record>` 而不是 `std::vector<Record*>`；vector 的析构函数会释放全部元素。
- **用工具尽早发现泄漏。** 在调试构建下用 AddressSanitizer（`-fsanitize=address`）或 Valgrind 运行，二者都会精确报告泄漏块是在哪里分配的。
- **把「看似无关紧要」的提前返回视为泄漏隐患。** 在 `new` 之后的任何 `return` / `break` / `continue` / 异常，除非对象由 RAII 拥有，否则都是潜在泄漏。

## 总结

C++ 里的内存泄漏很少是微妙的逻辑错误——它们是**所有权错误**。修复办法不是「更小心地记得调用 `delete`」，而是**停止手动管理内存**。把每个资源包进 RAII 类型（`std::unique_ptr`、`std::shared_ptr`、容器或自定义守卫），这样离开作用域（无论正常还是异常）时资源都会被自动释放。泄漏于是不再是运行时追查，而是编译期就不存在的问题。
