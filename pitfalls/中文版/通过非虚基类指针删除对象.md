# 通过非虚基类指针删除对象

## 1. 问题描述

在 C++ 中，若对象可能经由基类指针被删除，
基类析构函数必须是虚函数。

否则，`delete Base*` 指向 `Derived` 对象时将触发未定义行为（UB）。

该问题危险在于：

1. 编译通常不会报错；
2. 简单测试可能“看似正常”；
3. 线上可能以随机崩溃、泄漏、堆损坏形式出现。

---

## 2. 讨论边界

### 2.1 本文覆盖

1. 非虚析构删除为何是 UB；
2. 对象模型层面的根因；
3. 常见误解与替代方案；
4. 工程评审与迁移清单。

### 2.2 本文不覆盖

不讨论各平台 ABI 的具体布局实现。
重点是语言层面可依赖规则。

---

## 3. 最小示例

```cpp
struct Base {
    ~Base() = default; // 非虚析构
};

struct Derived : Base {
    ~Derived() { /* 释放资源 */ }
};

Base* p = new Derived;
delete p; // UB
```

静态类型是 `Base*`，动态类型是 `Derived`。
无虚析构时，删除路径无法保证按动态类型正确析构。

---

## 4. 为什么是未定义行为

多态删除本质上依赖动态分发析构链。

若基类析构非虚：

1. 删除表达式按静态类型路径处理；
2. 派生析构可能不被调用；
3. 资源释放与对象销毁流程失配；
4. 行为不再受标准保证。

这不是“可能泄漏”这么简单，而是正式 UB。

---

## 5. 对象模型视角

删除语义需要回答：“当前对象的真实动态类型是什么？”

虚析构的作用就是为基类删除提供动态绑定入口。
没有这个入口，`delete` 无法可靠完成最派生对象析构序列。

---

## 6. 常见表现

UB 没有固定症状，但常见后果包括：

1. 派生资源未释放导致泄漏；
2. 部分析构导致状态损坏；
3. 分配器元数据损坏引发延迟崩溃；
4. 仅在高优化或不同平台复现。

其隐蔽性使排障成本极高。

---

## 7. 正确规则

只要类可能作为多态基类被删除，必须：

```cpp
struct Base {
    virtual ~Base() = default;
};
```

这行声明是生命周期契约，不是风格偏好。

---

## 8. 若不打算多态删除

若类型不应被多态使用，可显式限制：

1. 类设为 `final`；
2. 析构设为 `protected`/`private` 并封装销毁路径；
3. 移除无必要虚函数。

“设计意图显式化”优先于隐含假设。

---

## 9. 高频错误模式

“基类有虚函数，但析构非虚”。

这会形成最危险组合：

1. API 鼓励多态使用；
2. 删除路径却不安全。

只要有虚函数的可扩展基类，通常就应配虚析构。

---

## 10. 接口基类示例

```cpp
struct ITask {
    virtual ~ITask() = default;
    virtual void run() = 0;
};
```

即使无成员数据，接口基类也需要虚析构来确保删除安全。

---

## 11. 智能指针也依赖析构合同

`std::unique_ptr<Base>` 默认删除器仍通过 `Base` 删除。
若 `Base` 析构非虚，问题不会因智能指针而自动消失。

智能指针解决“谁负责删”，
不解决“删的语义是否正确”。

---

## 12. 自定义删除器并非通用解

可用自定义删除器硬编码真实类型：

```cpp
std::unique_ptr<Base, void(*)(Base*)> p(
    new Derived,
    [](Base* b) { delete static_cast<Derived*>(b); }
);
```

但该方案脆弱：

1. 强耦合具体派生类型；
2. 动态类型变化时易出错；
3. 不适合开放层级。

工程上更推荐修正基类契约。

---

## 13. 受保护虚析构模式

某些框架希望限制外部删除权限，可使用：

```cpp
struct Base {
protected:
    virtual ~Base() = default;
};
```

这样保留动态析构语义，同时控制删除入口。
需配套明确所有权工厂/管理器设计。

---

## 14. 与构造/析构虚调用规则的区别

常见混淆：

1. 构造/析构期间虚调用不会下发到最派生覆写；
2. 多态删除需要虚析构。

二者是不同问题，不可互相替代解释。

---

## 15. ABI 与演进成本

对外发布库中，后补虚析构可能触发 ABI 变化。
因此基类多态删除策略应在设计早期确定。

“先不加，后面再补”在长期维护项目中代价很高。

---

## 16. 性能误解

有人担心虚析构有性能开销。
但在多态体系中，这点成本通常远小于错误删除带来的风险。

优先级应是：

1. 先保证语义正确；
2. 再基于数据做性能优化。

---

## 17. 与对象切片的关联

多态删除错误与对象切片常同时出现，
都源于对静态类型与动态类型关系理解不足。

统一治理思路：

1. 多态接口不按值传参；
2. 基类析构虚化；
3. 所有权模型显式化。

---

## 18. 旧代码迁移策略

1. 扫描所有存在继承层级的基类；
2. 标记可能被基类指针删除的类型；
3. 为其添加虚析构；
4. 验证测试、工具链与 ABI 影响；
5. 为非多态类型收紧继承与删除入口。

应分批迁移并配套回归测试。

---

## 19. 工具辅助

可启用编译器/静态分析规则检测：

1. 存在虚函数但析构非虚；
2. 可疑基类删除路径；
3. 不安全的所有权转换。

工具可提前暴露风险，但不能替代设计评审。

---

## 20. 代码评审清单

- [ ] 该基类是否用于多态？
- [ ] 是否存在经基类删除路径？
- [ ] 基类析构是否虚函数？
- [ ] 智能指针别名是否依赖正确删除合同？
- [ ] 所有权与销毁责任是否明确？
- [ ] 对外库是否评估 ABI 影响？

任一项模糊都应阻止合并。

---

## 21. 工程准则汇总

1. 多态基类必须虚析构；
2. 非多态基类避免暴露多态删除路径；
3. 智能指针不是析构语义修复器；
4. 将析构策略视为 API 合同的一部分；
5. 用规则与评审把问题前移到编译期和代码评审期。

---

## 22. 总结

通过非虚基类指针删除派生对象是 C++ 中的高危 UB。
它的可怕之处在于“看起来合理、运行时偶发失败”。

可靠规则非常简单且应制度化：

> 只要可能经由基类进行多态删除，基类析构函数必须是虚函数。

这条规则一旦被团队严格执行，可直接消除一整类生命周期灾难性缺陷。
