# 零法则、三法则与五法则

## 1. 引言

在 C++ 中，特殊成员函数不是样板代码。
它们直接定义类型的所有权语义、拷贝行为、移动行为与销毁责任。

当这些语义不清晰时，程序往往“能编译、能运行一段时间”，
但在压力场景下出现双重释放、悬垂访问或隐式性能退化。

零法则、三法则、五法则并非互斥口号，
而是回答同一个设计问题的分层规则：

> 这个类型是否直接拥有资源？如果拥有，拷贝/移动/销毁应如何定义？

---

## 2. 讨论边界

### 2.1 本章覆盖

1. 三条规则的语义边界；
2. 特殊成员函数的联动影响；
3. 所有权模型与规则选择；
4. 工程中的迁移与评审策略。

### 2.2 本章不覆盖

不逐条展开标准对“隐式生成”的全部措辞细节。
重点是可落地的工程推理。

---

## 3. 六个特殊成员函数

现代 C++ 中通常关注六个特殊成员：

1. 默认构造函数；
2. 析构函数；
3. 拷贝构造函数；
4. 拷贝赋值运算符；
5. 移动构造函数；
6. 移动赋值运算符。

它们的隐式生成存在联动关系。
手写其中之一，常会改变其余成员的可用性或默认语义。

---

## 4. 三法则（Rule of Three）

### 4.1 规则表述

若类型手写了以下之一：

- 析构函数，
- 拷贝构造，
- 拷贝赋值，

通常应完整定义三者。

### 4.2 背后原因

这三者在资源拥有类型中高度耦合。
只改一个、其余沿用默认，往往导致所有权语义断裂。

---

## 5. 五法则（Rule of Five）

C++11 引入移动语义后，
若类型需要手写拷贝/析构逻辑，通常还应显式处理：

- 移动构造；
- 移动赋值。

否则可能出现：

1. 类型意外不可移动；
2. 移动语义退化为昂贵拷贝；
3. moved-from 状态不明确。

---

## 6. 零法则（Rule of Zero）

零法则的核心是：

> 类型若不直接管理原始资源，就不应手写特殊成员函数。

推荐通过组合标准 RAII 类型承载资源：

- `std::vector`、`std::string`、`std::unique_ptr` 等。

这样可让编译器生成的默认语义天然正确。

---

## 7. 典型风险示例

```cpp
class Buffer {
public:
    explicit Buffer(std::size_t n)
        : n_(n), data_(new char[n]{}) {}

    ~Buffer() { delete[] data_; }

private:
    std::size_t n_{};
    char* data_{};
};
```

该类型定义了析构，却未定义拷贝控制。
默认拷贝会浅拷贝指针，最终双重释放（UB）。

---

## 8. 按五法则修正（显式资源管理）

```cpp
class Buffer {
public:
    explicit Buffer(std::size_t n)
        : n_(n), data_(new char[n]{}) {}

    ~Buffer() { delete[] data_; }

    Buffer(const Buffer& other)
        : n_(other.n_), data_(new char[other.n_]) {
        std::memcpy(data_, other.data_, n_);
    }

    Buffer& operator=(const Buffer& other) {
        if (this == &other) return *this;
        char* tmp = new char[other.n_];
        std::memcpy(tmp, other.data_, other.n_);
        delete[] data_;
        data_ = tmp;
        n_ = other.n_;
        return *this;
    }

    Buffer(Buffer&& other) noexcept
        : n_(other.n_), data_(other.data_) {
        other.n_ = 0;
        other.data_ = nullptr;
    }

    Buffer& operator=(Buffer&& other) noexcept {
        if (this == &other) return *this;
        delete[] data_;
        n_ = other.n_;
        data_ = other.data_;
        other.n_ = 0;
        other.data_ = nullptr;
        return *this;
    }

private:
    std::size_t n_{};
    char* data_{};
};
```

该写法正确，但复杂度与出错面都较高。

---

## 9. 更优方案：零法则组合

```cpp
#include <vector>

class Buffer {
public:
    explicit Buffer(std::size_t n) : data_(n) {}

private:
    std::vector<char> data_;
};
```

借助标准拥有型成员，拷贝/移动/析构语义由库类型保证。
这就是零法则的工程价值。

---

## 10. 所有权模型与规则映射

### 10.1 非拥有观察类型

例如 `std::string_view`、观察指针。
通常适用零法则。

### 10.2 唯一拥有类型

如句柄封装、独占资源管理。
若直接管理原始资源，常需五法则；
若由 `std::unique_ptr` 承载，可回归零法则。

### 10.3 共享拥有类型

需显式建模生命周期图并防循环引用。
优先使用标准共享设施。

---

## 11. 隐式生成的实用经验

标准细节复杂，但可遵循以下工程经验：

1. 手写析构后，应立刻审查 move 是否仍符合预期；
2. 手写拷贝成员后，不要假定 move 语义仍自然成立；
3. 任何特殊成员变更都应触发“所有权合同”复审。

---

## 12. `=default` 与 `=delete` 的价值

二者是语义声明工具，而非语法糖。

示例（move-only 类型）：

```cpp
class Handle {
public:
    Handle() = default;
    ~Handle() = default;

    Handle(const Handle&) = delete;
    Handle& operator=(const Handle&) = delete;

    Handle(Handle&&) noexcept = default;
    Handle& operator=(Handle&&) noexcept = default;
};
```

这样可避免“意外可拷贝/意外不可移动”的歧义。

---

## 13. 赋值操作与异常安全

拷贝赋值常应提供强保证。
推荐“先构建新状态，再提交”的模式，
避免异常导致对象进入半更新状态。

三/五法则不只是内存正确性问题，也直接关联异常安全等级。

---

## 14. `noexcept` 与移动语义

当移动确实不抛异常时，应标注 `noexcept`。
标准容器和泛型组件会据此选择迁移策略。

但 `noexcept` 不能虚假承诺。
错误标注会把可恢复错误升级为 `terminate` 风险。

---

## 15. 零法则的可维护性优势

零法则的本质收益：

1. 减少手写资源管理代码；
2. 降低语义回归概率；
3. 提升代码评审可读性；
4. 改动更局部，重构更安全。

---

## 16. 高频反模式

1. 原始拥有指针 + 自定义析构 + 默认拷贝；
2. 禁拷贝但漏定义移动，导致容器适配问题；
3. 移动后对象状态未定义且不可安全析构；
4. 拥有指针与观察指针混用且命名不区分。

---

## 17. 旧代码现代化路径

建议分阶段：

1. 识别原始拥有资源类型；
2. 明确每个类型的所有权合同；
3. 优先迁移到标准拥有型成员；
4. 用 `=default` / `=delete` 固化语义；
5. 增加拷贝/移动行为测试。

---

## 18. 值语义不是默认义务

不是每个类型都应可拷贝。
“可拷贝”本身是 API 合同，需要语义与成本都成立。

设计前应回答：

1. 拷贝是否有业务意义？
2. 深拷贝成本是否可接受？
3. 是否应设计为 move-only？

---

## 19. 特殊成员测试清单

资源拥有类型建议覆盖：

1. 拷贝构造后对象相互独立；
2. 拷贝赋值自赋值安全；
3. 移动构造后源对象仍可析构；
4. 移动赋值会正确释放旧资源；
5. 异常路径下无泄漏与不变式破坏。

---

## 20. 代码评审清单

合并前应核对：

- [ ] 类型是否直接拥有资源？
- [ ] 规则选择（零/三/五）是否明确且合理？
- [ ] 拷贝/移动语义是否与所有权合同一致？
- [ ] `noexcept` 标注是否正确？
- [ ] 原始指针是否区分拥有/观察语义？
- [ ] 重构是否改变了既有语义合同？

若评审者无法快速判断所有权，说明设计仍不够清晰。

---

## 21. 规则选择决策矩阵

可采用以下简化决策：

1. 不直接拥有资源 -> 零法则；
2. 直接拥有且需手写策略 -> 五法则；
3. 历史/教学语境下说明拷贝控制 -> 三法则框架；
4. 语义要求不可拷贝 -> 显式 `=delete` 拷贝，按需开放移动。

在类型初建阶段就做该决策，可显著降低后期返工。

---

## 22. 总结

零法则、三法则、五法则共同描述了同一条设计主线：

1. 能组合就组合，优先零法则；
2. 必须手写时就完整手写，不做半套；
3. 将所有权、拷贝、移动、销毁语义显式化并可测试。

现代 C++ 的默认答案通常是零法则。
一旦偏离零法则，就应有明确理由、完整实现和严格评审。
多数资源管理缺陷，恰恰源于“只改一半”的特殊成员设计。
