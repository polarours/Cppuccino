# 虚函数分发与对象模型

## 1. 引言

在 C++ 中，多态并不是“语法层面的便利功能”，
而是由对象模型、名称绑定与生命周期规则共同构成的运行时契约。

正确理解虚分发，必须同时考虑三个维度：

1. 调用点的静态类型；
2. 对象的动态类型；
3. 对象当前所处的生命周期阶段。

大量多态缺陷并非来自虚函数本身，
而是因为其中某个维度被忽略。

本章目标：

> 明确虚分发在何时发生、何时不会发生，以及生命周期如何约束所有多态行为。

---

## 2. 讨论边界

### 2.1 本章覆盖

- 虚分发的核心语言语义；
- 构造/析构阶段的分发规则；
- 对象切片与多态删除安全；
- `dynamic_cast` / `typeid` 的正确使用边界；
- 工程设计与评审清单。

### 2.2 本章不覆盖

不深入具体 ABI（如 vtable 布局细节）的平台差异实现。
重点是跨平台可依赖的语言层结论。

---

## 3. 基础术语

### 3.1 静态类型（Static Type）

由声明在编译期确定的类型。

```cpp
Base* p = ...; // p 的静态类型是 Base*
```

### 3.2 动态类型（Dynamic Type）

运行时对象的最派生类型。
若 `p` 实际指向 `Derived` 对象，则动态类型为 `Derived`。

### 3.3 多态类型（Polymorphic Type）

至少含一个虚函数的类。
只有多态类型才具备完整运行时类型识别能力。

---

## 4. 最小虚分发模型

```cpp
#include <iostream>

struct Base {
    virtual ~Base() = default;
    virtual void f() { std::cout << "Base\n"; }
};

struct Derived : Base {
    void f() override { std::cout << "Derived\n"; }
};
```

通过 `Base*` 或 `Base&` 调用 `f()`，若动态类型是 `Derived`，
则分发到 `Derived::f()`。

---

## 5. 动态分发成立条件

虚分发并非“只要写了 virtual 就必然发生”。
通常需要同时满足：

1. 调用目标是虚函数；
2. 调用经由基类引用/指针等多态语境；
3. 对象处于有效生命周期且分发语义可用。

若对象发生切片，或调用的是非虚函数，语义完全不同。

---

## 6. 构造与析构阶段的关键规则

在构造/析构过程中，虚调用**不会**分发到更派生层。

原因是语言要避免访问“尚未构造完成”或“已析构完成”的派生状态。

因此：

1. 基类构造函数中的虚调用只到达基类版本；
2. 基类析构函数中的虚调用也只到达基类版本。

这不是实现细节，而是标准语义。

---

## 7. 构造/析构分发示例

```cpp
#include <iostream>

struct Base {
    Base() { f(); }
    virtual ~Base() { f(); }

    virtual void f() { std::cout << "Base::f\n"; }
};

struct Derived : Base {
    void f() override { std::cout << "Derived::f\n"; }
};
```

构造 `Derived` 时，`Base` 构造中的调用输出 `Base::f`。
析构路径中到达 `Base` 析构时，调用仍输出 `Base::f`。

---

## 8. 多态基类的虚析构要求

若对象可能通过基类指针删除，基类析构必须是虚函数。

错误示例：

```cpp
struct Base {
    ~Base() = default; // 非虚析构
};

struct Derived : Base {
    ~Derived() { /* 释放资源 */ }
};
```

`delete Base*` 指向 `Derived` 时属于未定义行为。

正确写法：

```cpp
struct Base {
    virtual ~Base() = default;
};
```

---

## 9. 对象切片（Object Slicing）

多态依赖间接访问，不依赖值复制。

```cpp
void log(Base b); // 可能切片
```

若传入 `Derived`，按值复制会丢失派生部分。
之后再谈动态分发已无意义。

接口建议：

1. 多态参数用 `Base&` / `Base*`；
2. 值语义仅用于非多态值对象。

---

## 10. `override` 的工程价值

所有覆写函数应显式标注 `override`。

收益：

1. 防止签名细微偏差导致“未覆写”；
2. 在重构时提供编译期保护；
3. 提升代码评审可读性。

---

## 11. `final` 的设计意义

对不应再被继承或覆写的层级，可用 `final` 表达封闭设计。

```cpp
struct Leaf final : Base {
    void f() override;
};
```

`final` 首先是语义约束，性能收益属于附加结果。

---

## 12. 协变返回类型（Covariant Return）

虚函数覆写允许在返回指针/引用时使用协变返回：

```cpp
struct Base { virtual Base* clone() const = 0; };
struct Derived : Base { Derived* clone() const override; };
```

该模式常用于克隆接口，但所有权语义仍需明确（优先智能指针）。

---

## 13. RTTI、`dynamic_cast` 与 `typeid`

向下转型应优先使用可检查的 `dynamic_cast`。

建议：

1. 优先通过虚接口避免频繁向下转型；
2. 必须转型时，避免无证明的 `static_cast`。

`typeid` 在多态语境可反映动态类型信息。

---

## 14. 多重继承的复杂度

多重继承并非绝对禁用，但复杂度显著提升。
风险点包括：

1. 成员名歧义；
2. 基类子对象偏移调整；
3. 菱形继承中的共享基类策略。

若无明确收益，优先组合而非继承。

---

## 15. NVI（Non-Virtual Interface）模式

NVI 可将不变式控制与可扩展点分层：

```cpp
struct Base {
    void run() { pre(); do_run(); post(); }
    virtual ~Base() = default;

private:
    virtual void do_run() = 0;
    void pre();
    void post();
};
```

外部调用入口稳定，扩展点聚焦于 `do_run()`。

---

## 16. 纯虚函数与析构函数

即使析构函数声明为纯虚，也必须提供定义：

```cpp
struct Abstract {
    virtual ~Abstract() = 0;
};

inline Abstract::~Abstract() = default;
```

这是抽象基类设计中的常见误区。

---

## 17. 生命周期优先于分发机制

对象生命周期结束后，任何成员调用都无效，
虚分发机制无法“挽救” UAF（Use-After-Free）。

工程上应明确所有权：

1. 默认 `std::unique_ptr` 独占；
2. 共享时明确 `std::shared_ptr` 图结构；
3. 避免裸拥有指针。

---

## 18. 并发场景下的多态

虚调用本身不提供同步。
并发访问同一多态对象仍需线程安全协议。

应在接口中明确：

1. 成员函数并发调用是否安全；
2. 销毁与调用是否可能竞态；
3. 同步责任归属。

---

## 19. 性能认知（避免神话）

虚调用成本通常是一层间接调用与分支预测影响。
在大多数系统中，算法与数据布局常是更大瓶颈。

建议：

1. 先测量再优化；
2. 语义正确优先；
3. 在证据充分时再考虑替代方案（如静态多态）。

---

## 20. 高频反模式

1. 多态基类缺失虚析构；
2. 在构造/析构中依赖派生覆写逻辑；
3. 多态对象按值传递导致切片；
4. 无校验向下转型；
5. 生命周期合同不明确。

---

## 21. 方案选择矩阵

运行时多态适用于：

1. 行为集合开放扩展；
2. 分发需在运行时决定；
3. 对象身份与生命周期是核心。

若类型集合封闭且编译期可决策，可考虑静态方案（模板/variant）。

---

---

## 23. 工程建议汇总

1. 多态接口保持小而稳定；
2. 强制 `override`，按需 `final`；
3. 构造/析构中避免依赖虚分发；
4. 把生命周期合同当作一等公民；
5. 在可读性与可维护性前提下使用继承。

---

## 24. 总结

虚函数分发在 C++ 中是可预测且可靠的，前提是同时推理：

1. 静态类型，
2. 动态类型，
3. 生命周期阶段。

多数缺陷并非“虚函数不可靠”，而是违反了这三者的一致性。

当你把虚析构、反切片接口、构造/析构规则和显式所有权纳入统一设计，
多态就会从“潜在风险点”变成“可维护系统的稳定抽象能力”。
