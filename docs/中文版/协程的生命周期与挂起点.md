# 协程的生命周期与挂起点

## 1. 引言

C++20 协程（Coroutine）是无栈状态机。
它最难的部分并不是 `co_await` 语法本身，而是生命周期边界从“词法作用域”扩展到了“时间维度”。

在普通同步函数中，很多推理可以依赖作用域结构。
而在协程中，执行可能在任意挂起点暂停并在未来恢复，甚至由不同执行上下文恢复。

因此，协程正确性的核心可归纳为：

> 跨挂起点的数据、句柄与资源生命周期是否有明确且可验证的契约。

---

## 2. 讨论边界

### 2.1 本章覆盖

1. 协程帧中“什么会活下来”。
2. 哪些引用/视图会在挂起后悬垂。
3. 取消与错误传播如何影响生命周期。
4. 面向工程的 API 设计与评审规范。

### 2.2 本章不覆盖

不完整展开所有 awaiter/调度器实现细节，仅讨论影响正确性的最小必要语义。

---

## 3. 最小语义模型

### 3.1 协程的编译期转换

协程函数会被转换为状态机，核心包括：

- 协程帧（coroutine frame），
- `promise_type`，
- 挂起/恢复状态转移。

### 3.2 协程帧中通常包含什么

概念上，协程帧通常包含：

1. `promise_type` 状态，
2. 形参对象，
3. 跨挂起点仍需存活的局部对象，
4. 编译器维护的控制信息。

不跨挂起点的局部变量，可能不会保留到帧中。

### 3.3 帧销毁意味着什么

协程完成或显式销毁时，帧中对象按规则析构。
任何仍指向该帧内部的引用、指针、句柄都会失效。

---

## 4. `co_await` 的关键现实

`co_await expr` 语义上可能：

1. 不挂起并立即继续，
2. 挂起并在稍后恢复。

代码必须同时在两条路径上正确。
“这个 await 通常很快返回”不是正确性前提。

---

## 5. 参数生命周期：值、引用与视图

### 5.1 值参数

按值传入通常提供更稳健的生命周期边界。
若数据跨挂起点使用，值语义更容易保证安全。

### 5.2 引用参数

引用是借用关系，不拥有对象。
只有当被引用对象寿命覆盖所有恢复路径时才安全。

### 5.3 视图类型

`std::string_view`、`std::span`、迭代器等都属于借用视图。
它们不延长底层存储寿命。

---

## 6. 典型悬垂示例

```cpp
// 概念示例
task<void> bad(std::string_view sv) {
    co_await some_async_op();
    use(sv); // 若底层字符串已销毁，则为 UB
}
```

若调用端传入临时字符串，挂起后再恢复时 `sv` 可能悬垂。
这类缺陷常表现为偶发崩溃或数据污染。

---

## 7. 更安全的写法：跨挂起点优先拥有

```cpp
task<void> good(std::string s) {
    co_await some_async_op();
    use(s); // 自身持有存储，跨挂起点安全
}
```

按值传参可能增加一次拷贝/移动成本，但提供明确生命周期边界。
在工程实践中，正确性优先于微观性能假设。

---

## 8. 协程 Lambda 的捕获风险

当 lambda 本身成为协程时，捕获策略尤为关键。

```cpp
auto make_task() {
    int x = 42;
    return [&, x_copy = x]() -> task<void> {
        co_await some_async_op();
        use(x_copy); // 安全
        // 若使用外层局部变量的引用捕获，可能悬垂
    }();
}
```

经验法则：

- 只要任务可能逃逸当前作用域，默认避免引用捕获。

---

## 9. Awaiter 自身生命周期问题

`co_await` 背后是 awaiter 协议。
若 awaiter 内部保存了短生命周期引用，恢复阶段就可能读到失效数据。

设计 awaiter 时需满足：

1. 引用目标可达且稳定，
2. 回调捕获资源与完成时机匹配，
3. 销毁路径幂等且异常安全。

---

## 10. 线程/执行器语义必须文档化

协程本身不自动承诺“在同一线程恢复”。
恢复位置由 awaiter/执行器策略决定。

API 需明确：

1. continuation 在何处执行，
2. 是否可能发生上下文切换，
3. 共享状态需要哪些同步约束。

未声明的线程假设是并发缺陷的高发源头。

---

## 11. 取消（Cancellation）与生命周期耦合

取消不是“附加功能”，而是生命周期事件。

在取消路径中应保证：

1. 资源释放且仅释放一次，
2. 不暴露半销毁状态，
3. 停止回调与注册关系正确解绑定。

建议在测试中对每个 await 点注入取消场景。

---

## 12. 错误传播与清理一致性

协程异常可能跨挂起边界传播。
需要明确：

1. 错误如何通过任务结果通道暴露，
2. 帧销毁是否覆盖全部资源回收，
3. 是否错误依赖“正常恢复顺序”。

`final_suspend` 相关行为应在接口文档中明确给出。

---

## 13. 句柄（Handle）所有权模型

协程句柄可恢复、可销毁，能力强但风险高。
若多个组件都“认为自己拥有销毁权”，极易出现双重销毁或 UAF。

推荐模型：

- 唯一拥有者负责销毁，
- 观察者仅查询状态，
- 转移语义显式并可测试。

---

## 14. `initial_suspend` 与 `final_suspend` 的接口意义

这两个点直接影响上层调用语义：

1. 任务是 eager 还是 lazy 启动，
2. 完成何时对外可见，
3. 最终清理由谁接管。

若不明确，集成层经常出现行为不一致。

---

## 15. 可重入（Reentrancy）风险

某些 awaiter 可能“内联恢复”后续逻辑，导致可重入执行。
如果代码默认“恢复一定异步发生”，则状态机可能被破坏。

工程约束：

1. 不假设恢复一定延后，
2. 关键状态转移要防重入，
3. 对共享状态做原子化或序列化设计。

---

## 16. 高风险资源类型清单

跨挂起点常见风险资源：

1. 持锁对象（尤其在 `co_await` 前后跨越），
2. 指向容器元素的原始指针（容器可能变更失效），
3. 来自调用方栈对象的引用，
4. 指向临时对象的视图类型。

默认策略：避免持锁跨 `co_await`，除非有严格证明。

---

## 17. 调试现实：复现困难是常态

协程生命周期缺陷高度依赖调度时序。
调试器本身会改变时序，从而掩盖或放大问题。

建议组合策略：

1. 可控测试调度器，
2. 随机延迟压力测试，
3. Sanitizer 与竞态检测，
4. Debug 断言（生命周期与状态不变式）。

---

## 18. 协程 API 文档模板（建议固定化）

每个公开协程接口至少应说明：

1. 入参与返回任务的所有权语义，
2. 是否会在返回后继续保留入参引用/视图，
3. 取消与超时行为，
4. 恢复线程/执行器语义，
5. 完成与销毁责任归属。

这五项缺失时，调用方极易形成错误假设。

---

## 19. 实践模式

### 19.1 跨挂起点数据优先值语义

只要数据可能在 `co_await` 之后被访问，优先拥有它。

### 19.2 区分借用接口与拥有接口

可同时提供：

- 借用型高性能接口（附严格前置条件），
- 拥有型默认安全接口。

### 19.3 控制协程体规模

过长协程会掩盖挂起边界。
拆分小函数有利于评审与故障定位。

---

## 20. 借用/拥有双接口示例

```cpp
// 借用接口：调用者负责寿命覆盖
task<void> send_view(std::string_view payload);

// 拥有接口：默认安全
task<void> send_owned(std::string payload);
```

这种分层能把“性能-安全权衡”显式化。

---

## 21. 高频反模式

1. 将临时对象视图传给长生命周期协程。
2. 协程 lambda 通过引用捕获局部对象并逃逸。
3. 持锁跨挂起点。
4. 默认恢复线程与调用线程相同。
5. 将取消机制事后补丁式加入。

这些问题本质都是生命周期合同不完整。

---

## 23. 版本与可移植性备注

- 协程语言特性标准化于 C++20。
- 任务类型、执行器、取消模型属于库层生态，差异较大。
- 不应把某框架行为误当作语言层保证。

可移植性前提是把“语言语义”与“框架策略”严格分离。

---

## 24. 总结

协程将函数执行延展到时间维度，生命周期推理必须同步升级。

稳健的协程工程依赖四个清晰契约：

1. 数据由谁拥有，
2. 句柄由谁销毁，
3. continuation 在何处执行，
4. 取消与错误如何结束生命周期。

当这些契约被显式定义、文档化并可测试时，协程才是可维护的工程能力；
若契约隐含不明，问题将长期潜伏且难以复现。
