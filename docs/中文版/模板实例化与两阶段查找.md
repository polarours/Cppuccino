# 模板实例化与两阶段查找

## 1. 引言

C++ 模板的强大之处在于“延迟到具体类型再求值”。
但这也带来一个经常被忽略的事实：

> 模板在定义阶段与实例化阶段执行不同层次的名称查找与语义检查。

这一机制即“两阶段查找（Two-Phase Lookup）”。
若将两阶段混为一谈，常见后果是：

1. 错误信息延迟且难定位；
2. 代码在不同编译器下表现不一致；
3. 泛型接口可维护性快速下降。

本章目标是建立可操作的工程认知：

1. 哪些名称在定义时就必须成立；
2. 哪些名称会延迟到实例化时解析；
3. 如何让模板错误“尽早、可读、可维护”。

## 3. 两阶段语义模型

### 3.1 定义阶段（Template Definition Time）

模板被解析时：

1. 非依赖名立即查找并检查；
2. 语法与即时上下文合法性被确认；
3. 依赖表达式保留到后续实例化再处理。

### 3.2 实例化阶段（Instantiation Time）

当模板参数替换完成后：

1. 依赖名进行查找；
2. 依赖表达式执行类型检查；
3. 替换失败可能触发 SFINAE 或硬错误。

很多“看起来离定义处很远”的错误，正是实例化阶段才暴露。

---

## 4. 依赖名与非依赖名

### 4.1 非依赖名

不依赖模板参数的名称。
必须在模板定义点就能解析成功。

### 4.2 依赖名

依赖模板参数才能确定含义的名称。
在实例化阶段解析。

示例：

```cpp
template <typename T>
void print_size() {
    std::size_t n = T::size();
    (void)n;
}
```

- `std::size_t` 是非依赖名；
- `T::size` 是依赖名。

---

## 5. `typename` 的必要性

对依赖限定名，编译器默认无法判断其是否为类型。

```cpp
template <typename T>
void f() {
    typename T::value_type x{};
    (void)x;
}
```

若缺少 `typename`，解析会失败。

实践规则：

- 依赖限定类型名前，通常需要显式加 `typename`。

---

## 6. `template` 关键字的消歧义作用

依赖对象上的模板成员调用需要显式 `template`：

```cpp
template <typename T>
void g(T& t) {
    t.template apply<int>(42);
}
```

否则 `<` 可能被解释为比较运算符。

---

## 7. 依赖基类查找陷阱

经典问题：派生模板访问依赖基类成员。

```cpp
template <typename T>
struct Base {
    void foo() {}
};

template <typename T>
struct Derived : Base<T> {
    void bar() {
        // foo();   // 常见查找失败
        this->foo(); // 正确
    }
};
```

推荐显式使用 `this->` 或 `Base<T>::`。

---

## 8. ADL 与模板查找交互

参数相关查找（ADL）常见于泛型交换等自定义点。

```cpp
using std::swap;
swap(a, b);
```

这种写法允许：

1. 用户类型自定义 `swap` 参与 ADL；
2. 没有自定义时回落到 `std::swap`。

若强行写 `std::swap(a, b)`，可能阻断用户扩展点。

---

## 9. 为什么错误经常“远离定义点”

模板定义阶段可能完全通过，
但在某个具体类型实例化时失败。

这是两阶段查找的正常结果，不是编译器随机行为。

工程含义：

1. 模板应保持短小；
2. 约束尽量前置；
3. 复杂依赖逻辑要拆分。

---

## 10. C++20 约束前置（Concepts）

```cpp
#include <concepts>

template <typename T>
concept HasSize = requires { T::size(); };

template <HasSize T>
void print_size2() {
    auto n = T::size();
    (void)n;
}
```

这样可将错误尽量定位在“约束不满足”，
而不是深层实例化栈。

---

## 11. C++20 之前的约束策略

在旧标准中，可用 `static_assert` + traits 检查。

```cpp
template <typename T>
void h() {
    static_assert(sizeof(T) > 0, "T must be complete");
}
```

虽然表达力不如 Concepts，但仍能显著改善诊断可读性。

---

## 12. SFINAE 与硬错误边界

替换失败若发生在“即时上下文”，可触发 SFINAE（候选移除）。
若超出该边界，通常直接成为硬错误。

工程建议：

1. 优先显式约束，减少隐式 SFINAE 技巧；
2. 不要让 API 选择依赖难读的替换细节。

---

## 13. 让依赖逻辑局部化

大型模板函数会制造“错误爆炸”。
建议结构：

1. 对外接口负责约束；
2. 内部实现拆分为小型辅助函数；
3. 每层只承担单一依赖判断。

---

## 14. 分层示例

```cpp
template <typename T>
concept Streamable = requires(std::ostream& os, const T& v) {
    { os << v } -> std::same_as<std::ostream&>;
};

template <Streamable T>
void dump(const T& v) {
    dump_impl(v);
}

template <typename T>
void dump_impl(const T& v) {
    std::cout << v << '\n';
}
```

错误会更接近接口边界，便于使用者理解。

---

## 15. Hidden Friend 与查找策略

类内定义的友元函数（hidden friend）可通过 ADL 被发现。
常用于运算符重载扩展。

该技术有效但隐蔽，
若团队未统一规范，容易造成可读性与可维护性问题。

---

## 16. 可移植性提示

历史上，不同编译器对严格两阶段查找支持存在差异。
现代工具链已显著收敛，但非标准写法仍会产生跨编译器分歧。

建议：

1. 严格书写 `typename` / `template` / `this->`；
2. 避免依赖编译器扩展；
3. 早期进行多编译器 CI 验证。

---

## 17. 高频反模式

1. 依赖类型名前漏写 `typename`；
2. 依赖模板成员调用漏写 `template`；
3. 依赖基类成员访问未显式依赖化；
4. 无约束大模板导致诊断不可读；
5. 用复杂元编程替代更清晰的 Concepts。

---

## 18. 故障排查流程

遇到模板查找错误时可按以下顺序：

1. 判定名称是依赖还是非依赖；
2. 补齐 `typename` / `template`；
3. 审查依赖基类成员访问是否使用 `this->`；
4. 增加或强化约束；
5. 缩减到最小可复现模板。

这种流程比“试错式改动”更稳定。

---

## 19. 代码评审清单

- [ ] 依赖类型名是否正确使用 `typename`？
- [ ] 依赖模板成员调用是否使用 `template`？
- [ ] 依赖基类成员访问是否显式化？
- [ ] 约束是否在接口边界前置？
- [ ] 诊断信息是否对调用方友好？
- [ ] ADL 行为是否有意设计并文档化？

若以上任一项不清晰，应先重构再扩展功能。

---

## 20. 工程策略汇总

1. 模板接口先约束，再实现；
2. 依赖名处理显式化，不依赖隐式规则；
3. 实现拆小，提高诊断质量；
4. 将两阶段查找视为正确性模型，而非编译器怪癖；
5. 追求“可诊断性”与“可移植性”并重。

---

## 21. 迷你案例

```cpp
template <typename T>
struct Adapter : T {
    void call() {
        this->run();
    }
};
```

该例极短，却覆盖了依赖基类查找的核心陷阱。
许多真实项目问题都可归结到这一类模式。

---

## 22. 总结

两阶段查找是 C++ 模板语义一致性的基础机制。
它决定了“何时检查、何时报错、如何解析依赖名”。

高质量泛型代码应做到：

1. 依赖关系显式；
2. 约束前置明确；
3. 实现模块化且诊断友好。

当团队把这些原则固化为编码规范后，
模板代码会在可移植性、可维护性与错误定位效率上显著提升。
