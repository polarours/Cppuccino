# 拷贝消除与 prvalue 实体化

## 1. 引言

在现代 C++ 中，“拷贝消除”不再只是优化技巧。
从 C++17 开始，其中一部分行为已上升为语言语义本身。

很多误解来自旧模型：

1. 先构造临时对象，
2. 再拷贝/移动到目标，
3. 最后由编译器“可能”优化掉。

这套叙事在 C++17+ 的关键场景下并不准确。

本章关注一个工程目标：

> 明确对象究竟在何处被构造、何时被实体化，以及为什么拷贝/移动构造有时不会参与。

---

## 2. 讨论边界

### 2.1 本章覆盖

1. C++17 前后拷贝消除认知差异。
2. prvalue 实体化（materialization）模型。
3. 保证拷贝消除与非保证场景的边界。
4. 对 API 设计与代码评审的直接影响。
5. 常见性能测试误区。

### 2.2 本章不覆盖

不逐条复盘所有历史标准措辞，仅保留与工程实践高度相关的结论。

---

## 3. 术语先行：避免概念混用

### 3.1 拷贝消除（Copy Elision）

本质是“直接在目标存储上构造对象”，从而省去中间拷贝/移动步骤。

### 3.2 RVO 与 NRVO

- **RVO**（Return Value Optimization）：返回临时对象时的优化/语义路径。
- **NRVO**（Named Return Value Optimization）：返回具名局部对象时的优化路径。

### 3.3 实体化（Materialization）

prvalue 在某些上下文下可先作为“纯值计算结果”存在，不立即对应独立对象。
仅在需要对象身份或存储时才实体化。

---

## 4. C++17 前后认知差异

### 4.1 C++17 之前的常见解释

“先有临时对象，再看编译器是否把拷贝/移动优化掉。”

这种解释在教学上直观，但会诱导两个问题：

1. 过度依赖构造/移动次数作为语义证据；
2. 把“语言保证”与“实现优化”混为一谈。

### 4.2 C++17+ 的核心转变

在关键场景下，语言直接定义为“构造到最终目标位置”。

结果是：

- 可能根本不存在中间对象；
- 拷贝/移动构造即使存在也不一定被要求；
- 删除拷贝/移动构造并不必然导致返回值写法失效。

---

## 5. 保证场景：经典示例

```cpp
struct Widget {
    Widget() = default;
    Widget(const Widget&) = delete;
    Widget(Widget&&) = delete;
};

Widget make_widget() {
    return Widget{};
}
```

在 C++17+ 中，该返回形式可直接在调用方目标存储中构造 `Widget`。
因此不要求调用拷贝/移动构造函数。

---

## 6. 返回形式并不等价

### 6.1 返回临时 prvalue

```cpp
T f() {
    return T{};
}
```

这是 C++17+ 下讨论保证语义时最典型的路径。

### 6.2 返回具名局部对象

```cpp
T g() {
    T obj;
    return obj; // NRVO 候选
}
```

NRVO 在主流编译器上常见，但应区分：

- 哪些是语言保证，
- 哪些是实现选择。

工程正确性不得依赖“某个编译器恰好做了 NRVO”。

---

## 7. prvalue 实体化模型的工程意义

### 7.1 prvalue 不等于“立即有对象”

prvalue 可先是纯值语义，在确有对象需求时才实体化。

### 7.2 这会改变哪些习惯

1. 不再把“临时对象链条”当作唯一解释框架。
2. 不再依赖构造计数证明语言本质。
3. 把推理中心从“调用了几次 move”转到“对象生命周期与存储位置”。

---

## 8. 与删除拷贝/移动构造的交互

下面代码在 C++17+ 常可成立：

```cpp
struct X {
    X() = default;
    X(const X&) = delete;
    X(X&&) = delete;
};

X make_x() {
    return X{};
}
```

关键原因不是“编译器够聪明”，而是该语境下本就不要求中间拷贝/移动。

---

## 9. 返回语句中的 `std::move`

### 9.1 常见误用

```cpp
T f() {
    T t;
    return std::move(t);
}
```

这种写法可能破坏原本可获得的优化路径，且可读性下降。

### 9.2 实践建议

若无明确理由，返回局部对象时优先 `return t;`。
不要把 `std::move` 当成“必须加”的性能按钮。

---

## 10. 构造函数副作用不是语义证据

使用日志或计数器观察构造/移动调用次数，常用于调试，但不应上升为语义证明。

原因包括：

- 优化级别差异，
- 编译器实现差异，
- as-if rule 下可观察行为边界。

结论应来自标准语义，而非偶然输出。

---

## 11. 对 API 设计的直接影响

### 11.1 值返回通常是好默认

在现代语义下，值返回兼具可读性与性能潜力，常优于过度借用/裸指针接口。

### 11.2 避免“为移动而移动”

手工插入移动逻辑并不总能提升性能，反而可能增加语义噪音。

### 11.3 正确性与优化解耦

即便某些路径高度依赖编译器优化才能“快”，也不能让代码“只有在优化触发时才正确”。

---

## 12. 异常安全视角

直接构造到目标位置，并不改变异常安全基本原则：

1. 构造成功即建立不变式，
2. 析构负责释放拥有资源，
3. 失败路径可依赖语言保证进行正确回收。

异常安全结论不应建立在“中间临时对象是否存在”的猜测上。

---

## 13. 性能测量误区

### 13.1 Debug 观察误导

Debug 构建下常见“构造次数偏多”并不代表发布构建的真实行为。

### 13.2 微基准过拟合

极小样例可能只放大某个编译器版本的局部策略，难以代表真实业务路径。

### 13.3 推荐方式

综合使用：

- 目标优化等级构建，
- 汇编/IR 级别检查，
- 真实场景 profiling。

---

## 14. 代码评审中的高频误判

1. 把“语言保证”说成“编译器优化掉了”。
2. 把 NRVO 当作所有返回语句的强保证。
3. 在返回语句中机械插入 `std::move`。
4. 以构造日志次数作为跨平台结论依据。

评审语言应明确：哪些是标准保证，哪些是实现可选。

---

## 15. 版本一致性检查

在得出结论前，先确认：

1. 项目目标标准是否为 C++17 或更高。
2. 当前代码是否处于保证场景。
3. 讨论对象是“语义”还是“实现优化”。
4. 是否错误依赖了 debug 输出。

任一项不明确，都应在文档中写出前置条件。

---

## 16. 对比示例（建议在评审中直接引用）

```cpp
struct T {
    T();
    T(const T&);
    T(T&&);
};

T a() {
    return T{}; // C++17+ 关键保证语境
}

T b() {
    T t;
    return t;   // NRVO 候选
}

T c() {
    T t;
    return std::move(t); // 显式 xvalue，可能影响优化路径
}
```

三者语义与优化潜力不同，不应混写为同一模式。

---

## 17. 工程准则

1. 优先写清晰的值返回接口。
2. 避免习惯性在返回语句中使用 `std::move`。
3. 不将构造次数作为正确性前提。
4. 结论必须标注目标 C++ 版本。
5. 将 NRVO 视为性能收益，而非正确性依赖。

---

## 19. 总结

拷贝消除与 prvalue 实体化是现代 C++ 对象模型的核心组成，不应再被简化为“编译器会不会聪明优化”。

更稳健的工程方法是：

- 从生命周期与存储位置推理，
- 将标准保证与实现优化严格分层，
- 让 API 正确性独立于构造/移动次数的偶然表现。

当这一方法成为团队共识，值语义代码就能同时保持清晰性、可维护性与性能可预测性。
